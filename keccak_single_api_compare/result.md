# 단일 키생성·서명·검증 API 실측 — 2026-09-30

## 결론

**이번 조건에서는 기존 단일 API가 빨라지지 않았다.**

1. `keccak_test_batch4`를 단일 API로 사용하면 원본과 사실상 동일하다.
   x4 계산과 배치 API는 호출되지 않으며, 실제 ELF에서도 제거되어 있다.
2. 별도로 기존 단일 상태 MVE A14 후보도 측정했지만, 이 전체 API 실행 문맥에서는
   키생성·서명·검증이 모두 느렸다. 원본/A14를 한 번씩 더 측정해 같은 경향을 확인했다.
3. **`Final_code/Before_slothy`에는 아무 변경도 반영하지 않았다.**
   두 후보의 암호 소스도 수정하지 않았고, 이 디렉터리에 측정 프로그램/기록만 추가했다.

기준은 최초 `M55_ref`가 아니라 NTT/FFT가 이미 최적화된 현재 `Before_slothy`다.
배율 = 원본 cycles / 후보 cycles. 1 미만이면 느린 것이다.

batch4의 차이는 키생성에서 몇 cycles, 서명에서 약 49~68 cycles,
검증에서 약 6 cycles 수준이다. **실용적인 성능 개선이 없다**고 해석한다.
직전 독립 서명 네 건 배치의 1.0402×/1.0189×를 단일 서명에 적용하면 안 된다.

### 실제 cycles

각 입력의 3회 측정 중앙값을 구한 다음, 8개 입력의 중앙값들을 산술평균했다.
키생성의 입력별 재시도 차이를 없애려고 서로 다른 입력의 최소값을 고르지 않았다.

## 무엇을 바꾸지 않고 확인했나

- 기존 `fndsa_keygen_seeded_temp()`, `fndsa_sign_seeded_temp()`,
  `fndsa_verify_temp()`의 API와 호출 단위를 그대로 사용했다.
- 동일한 caller seed와 임시 배열을 사용했다. 시스템 RNG 시간과 convenience
  wrapper의 동적 스택 할당 비용은 이 측정의 대상이 아니다.
- `batch4`는 원래 single SHAKE 경로로 실행된다. x4 난수열을 억지로 한 요청에
  섞거나 배치 API를 감싸서 단일 API인 것처럼 측정하지 않았다.
- A14 폴더의 빌드에 들어가는 다른 암호 C/H/S는 `Before_slothy`와 같음을 확인했다.
  변경점은 기존 `sha3_cm55.s`를 쓰는 단일 Keccak 경로다.
- 소스와 심볼 감사 통과: 공통 함수/주요 배열·스택 **119개 named symbol의 주소·크기
  동일**. 변경 가능한 Keccak/서명 오브젝트 영역은 별도 고정 slot에 배치했다.
  이 검사는 모든 기계어 바이트가 동일하다는 뜻은 아니다.

## 이전 A14 커널 수치와 다른 이유에 대한 판단

이전 `process_block()` 단독 시험의 약 1.07배 결과를 이 전체 API에 그대로
대입할 수 없다. 같은 A14 소스여도 측정 문맥이 다르다.

- 이전 독립 커널 시험은 상태와 측정용 스택을 낮은 DTCM에 고정했다.
  특히 측정용 스택 상단은 `0x30005000`이었다.
- 이번에는 실제 API가 일반 서명/키생성 호출 스택에서 SHAKE를 부른다.
  세 이미지의 main stack은 모두 `0x3002c698`부터 64 KiB이며 상단은 `0x3003c698`이다.
- 상수/코드 위치, 호출 문맥, interrupt 정책도 이전 독립 커널 시험과 다르다.
  이번 **세 API 비교군 사이**에서는 같은 정책/주소를 맞췄다.

이 차이가 시간 증가의 어느 부분을 유발했는지는 **이번에 원인별로 분리 측정하지 않았다.**
따라서 스택 위치나 특정 하드웨어 병목이 확정 원인이라고 단정하지 않는다.
원본과 A14의 반복 측정으로 전체 API의 저하는 재현됐으므로, 현재 단일 API용으로
그대로 채택할 근거는 없다. 추가 원인 분석/수정은 이번 확인 작업에 포함하지 않았다.

## 정확성 및 시험 조건

각 최종 펌웨어 실행에서:

- 512/1024 각 8개 고유 입력, 총 **16개 입력**.
- warm-up 포함 **키/서명 출력 digest 대조 각각 64/64 통과**.
  host의 원본 `fn-dsa_ref`가 생성한 전체 sk||pk 및 signature SHAKE256 digest 기준.
- 별도 정상 서명 검증 64회, 서명/메시지 변조 거부 128회, scratch guards 통과.
  이에 더해 측정 루프에서 32회씩 반복 검증했다.
- CFSR/HFSR/AFSR=0, 시작·종료 TCM/ECC 설정 확인 통과.
- 이는 지정 입력의 회귀 검사이며 기존 전체 300/90 KAT suite 재실행이나
  상수시간·부채널 검증 완료를 의미하지 않는다.

환경:

- 실물 NUCLEO-N657X0-Q, ST-Link `003C00223335510735383531`.
- CPU 800 MHz, cache OFF, ITCM/DTCM 각 256 KiB, TCM ECC ON.
- 코드 ITCM, 상수/데이터/스택 DTCM. main stack 64 KiB.
- GCC 15.2.1, `-O3 -mcpu=cortex-m55 -mfpu=fpv5-d16 -mfloat-abi=hard`,
  `-ffp-contract=off -fno-fast-math -fno-strict-aliasing`.
- 동일 64-bit `k_cycle_get_64()` timer, interrupt/SysTick **ON**.
  장시간 키생성에서 32-bit cycle overflow를 피한다. 이전 batch4 시험의
  DWT/interrupt OFF 방식과 다르므로 그 표와 raw cycles를 직접 혼합하지 않는다.
- 각 크기/API당 24개 timed 호출(8입력×3회), 입력별 warm-up 1회.
  검증은 timed 호출 한 개가 32회 반복 평균이다.
- 세 시험 이미지의 예약 크기 동일: ITCM **128,652 bytes**, DTCM **247,448 bytes**.
  정렬/고정 slot padding과 테스트 데이터를 포함하므로 라이브러리의 최소 크기가 아니다.
