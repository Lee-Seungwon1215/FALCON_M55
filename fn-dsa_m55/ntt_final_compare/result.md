# NTT 최적화 전 원본 vs 최종 Slothy 통합본 — 동일 조건 재측정

2026-09-17 KST. **두 구현을 동일 측정 프로그램·동일 링크 배치 정책으로 새로 빌드하고,
같은 NUCLEO-N657X0-Q에서 크기·연산별 100회씩 실측 완료했다.** 과거 결과를 재사용한 표가 아니다.

## 비교 대상

- 원본 `ref`: 현재 경로는 `../M55_ref`. 과거 `fn-dsa_m55/ref` 측정 당시
  매니페스트와 루트 C/H/S 30개 해시가 모두 일치한다. 공통 q-NTT는 기존
  M4 어셈블리, RNS NTT는 기존 C이며 M4 인라인 어셈블리와 GCC의 M55 자동
  최적화는 유지했다. 강제 스칼라 빌드가 아니다.
- 최종: `../ntt_opt_slothy`의 실제 C/H/S 31개를 직접 컴파일했다.
  공통 q-NTT Slothy A + K4-C 기반 RNS Slothy A다.
  검증된 `ntt_ntrusolve/ref_slothy` 소스와 동일하지만, 이번 수치는 그 과거
  측정값이 아니라 `ntt_opt_slothy`에서 새로 만든 ELF의 실측이다.
- 암호 소스를 수정하지 않았으며, 외부 후보의 구현 조각을 가져오지 않았다.

## 1. 주 결과 — 전체 API 100회 산술평균

단위 cycles/call, 작을수록 빠르다. **NTT 커널만의 시간이 아니라 전체
키생성·서명·검증 API 시간**이다. 10개 고정 입력 × 입력별 10회 = 100회이며,
각 입력에 대해 별도 10회 워밍업을 수행했다.

| 크기 | 연산 | 최적화 전 ref | 최종 ntt_opt_slothy | 사이클 감소율 | 속도 배수 |
|---:|---|---:|---:|---:|---:|
| 512 | 키생성 | 57,447,592.09 | 51,471,982.26 | 10.4018% | 1.1161배 |
| 512 | 서명 | 18,265,777.46 | 17,966,440.59 | 1.6388% | 1.0167배 |
| 512 | 검증 | 366,759.01 | 315,677.10 | 13.9279% | 1.1618배 |
| 1024 | 키생성 | 280,951,478.44 | 260,891,457.64 | 7.1400% | 1.0769배 |
| 1024 | 서명 | 39,215,814.21 | 38,592,060.50 | 1.5906% | 1.0162배 |
| 1024 | 검증 | 725,746.21 | 618,877.26 | 14.7254% | 1.1727배 |

사이클 감소율 = `(ref − 최종) / ref × 100`, 속도 배수 = `ref / 최종`.
이 표의 기준은 NTT 최적화 전 원본이며 K4-C, M0, Slothy A/B 실험의 baseline이 아니다.

**이 동일 조건 실험에서는 서명도 약 1.6% 개선됐다.** 앞서 서로 다른 링크 배치의
과거 기록을 비교해 보였던 서명 3.34%/3.53% 저하는 재현되지 않았다. 그 과거 차이를
NTT 최적화에 따른 본질적 성능 저하로 해석하지 않는다. 이번 결과는 배치 영향을
통제한 누적 최적화 비교이며, 과거 차이의 모든 세부 원인을 독립적으로 증명한 것은 아니다.

## 2. 기존 보고 방식 — batch upper median 참고

과거 결과와 통계 정의를 혼동하지 않도록 함께 기록한다. 10개 batch total을
정렬한 여섯 번째 값을 10으로 나누고 정수로 내린 값이다. 100개 개별 호출의
중앙값이나 위 산술평균과는 다르다.

| 크기 | 연산 | ref upper median | 최종 upper median | 사이클 감소율 |
|---:|---|---:|---:|---:|
| 512 | 키생성 | 51,999,295 | 46,120,027 | 11.3064% |
| 512 | 서명 | 18,292,014 | 17,992,688 | 1.6364% |
| 512 | 검증 | 372,503 | 321,432 | 13.7102% |
| 1024 | 키생성 | 261,461,719 | 242,590,271 | 7.2177% |

키생성은 입력별 후보 재시도 횟수가 달라 평균과 대표값 차이가 크다. 비교군 간에는
동일 seed를 사용하고 같은 통계끼리 비교했다. 100개 독립 무작위 입력의 모집단
성능 추정이나 신뢰구간을 주장하지 않는다. 측정 순서는 ref → 최종이며 역순 100회
추가 실험은 수행하지 않았다.

| 구현 선택 차이 | ref는 `mq_cm4.s` + 기존 RNS C, 최종은 `mq_cm55.s` + `kgen_mp31_cm55.s`; 최종에만 `FNDSA_MVE_MP31=1` |
| 메모리 | 코드 ITCM, 전역 상수·데이터·스택 DTCM, 각 256 KiB 구성 |

`mlkem-native` Nucleo pin `637d076aa113d8faaec2277ed4a46b657acaf35f` 기반 환경을 유지했다.
상수를 DTCM으로 옮기는 기존 ECC 대응은 유지했으므로 무수정 upstream 배치와
동일하다고 주장하지 않는다. M4 보드는 사용하지 않았으며 Flash 쓰기·지우기 없이 RAM 적재했다.

### 공통 배치 정책

동일한 linker script에서 q 연산 객체 코드 12 KiB, RNS 객체 코드 8 KiB,
NTT 관련 객체 상수 24 KiB를 각각 같은 위치에 예약했다. 큰 최적화 코드 때문에
그 뒤의 FFT·sampler·측정 루프·작업 버퍼가 다른 주소로 밀리는 것을 방지했다.

- q 객체 코드 시작: `0x10000400`.
- RNS 객체 코드 시작: `0x10003400`.
- 나머지 코드 시작: `0x10005400`.
- NTT 상수 영역 시작: `0x30000a00`, 나머지 상수 시작: `0x30006a00`.
- 나머지 함수 **256개**의 주소·크기 일치.
- 나머지 상수·데이터 심벌 **146개**의 주소·크기 일치.
- SK/PK/서명/tmp/측정 버퍼 및 메인 스택 주소 일치.

각 구현의 **변경된 객체 내부 함수·상수 오프셋까지 같다는 뜻은 아니다**.
원본과 최적화 함수 길이/구조 자체가 다르다. 정책·공통 코드/데이터 배치를 맞춘
실험이며, 모든 주소를 동일하게 만든 명령 단위 실험으로 과장하지 않는다.
[ELF 배치 감사](results/layout_audit.json).

## 4. 검증 결과

- 두 ELF 모두 사전검사 후 본 측정: 정상 종료 0, 정합성 PASS.
- 각 본 측정의 프로젝트 고정-seed DIGEST/AUDIT **22개**가 host 기대값과 일치하고,
  두 구현끼리도 모두 일치한다. 공식 인증 KAT 전체 통과를 뜻하지 않는다.
- q-NTT 512/1024 독립 oracle·왕복 검사: 불일치 0, 최대 모듈러 오차 0.
- 최종 Barrett root/twist 상수곱 검사: 크기별 2,048쌍 불일치 0.
- 정상 서명검증 및 크기별 10개 batch의 변조서명 거부 PASS.
- `CFSR=HFSR=AFSR=0`, 시작/종료 TCM 설정·ECC 유지.
- 빌드·측정 전후 암호 소스 해시 동일. 최종 q/RNS 어셈블리는 기존 검증된
  Slothy A와 동일하며 이번에 새로운 암호 명령이나 비밀 의존 분기를 추가하지 않았다.
- RNS 308개 소수 전수 테스트와 정적 상수시간 검토는 같은 채택 소스의
  [이전 기록](../ntt_ntrusolve/ref_slothy/result.md)을 유지한다. **이번 성능 펌웨어에서는
  RNS 전수 검사를 다시 실행하지 않았다.** 형식적 CT 증명·dudect·전력/EM 검사는 아니다.
