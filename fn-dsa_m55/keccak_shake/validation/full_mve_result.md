# 초기 A0 전체 MVE Keccak 구현 결과 — 보존 기록

**이 문서는 17,689-cycle A0의 과거 기록이다. 현재 코드는 후속 A14(12,504 cycles)이며,
현재 결과·원인 분석은 [후속 보고서](full_mve_optimization.md)를 참조한다.**
아래의 “현재”·“아직 미측정” 및 정적 감사 링크는 A0 작성 당시를 뜻한다.
현재 static_audit.json은 새 최종 소스의 감사 결과로 갱신되어 있다.

측정일: 2026-09-29. 요청 범위인 입출력·비트 분리/복원, θ·ρ·π,
χ·다음 라운드 열 XOR 누적을 **모두 MVE 정수 ASM으로 구현했다**.
본문과 상수표는 [sha3_cm55.s](../sha3_cm55.s)에 직접 작성했다.
**기능 검사는 통과했지만 기존 혼합형보다 느리다.**
전체 MVE 소스를 이 경로에 유지했으며 성능 기준의 최종 채택으로 간주하지 않는다.

## 실제 변경 내용

| 구간 | 구현 | 스칼라 상태 계산 |
| --- | --- | --- |
| 입력·출력 | 공개 인덱스 MVE gather/scatter | 없음 |
| 비트 분리 | `K_SPLIT4`: shift·AND·OR로 네 64비트 값을 even32/odd32로 분리 | 없음 |
| 비트 복원 | `K_MERGE4`: 역방향 마스크·shift·OR | 없음 |
| 초기 열 parity | `K_INITIAL_PARITY`: 앞 네 열과 다섯 번째 열 모두 벡터 XOR | 없음 |
| θ | `K_THETA`: 네 보정값 병렬 계산, 다섯 번째도 벡터 계산 | 없음 |
| θ 주입·ρ·π | `K_RHOPI4`: 상수 gather·벡터 XOR·lane별 shift/OR 회전·벡터 저장 | 없음 |
| χ | `K_CHI_ROW`: VBIC/VEOR, 꼬리 `[4,0,1,2]`도 벡터로 계산 | 없음 |
| 다음 열 parity | `K_CHI_PLANE`: χ 결과를 벡터 XOR로 누적 | 없음 |
| ι | 활성 lane 2개의 MVE XOR로 A[0]/C[0] 반영 | 없음 |

주소 계산·상수표 포인터·공개 24라운드 카운터·스택 정렬·ABI 저장/복귀는
스칼라다. 스칼라를 완전히 없앤 ISA 프로그램이라는 뜻은 아니다.
FP32/FP64 산술, SLOTHY, x4 독립 상태 처리, 후보 선택 분기는 없다.

원래 private `bit_split_*` / `bit_merge_*` 정의는 비교·회귀검사 목적으로
그대로 남아 있지만 **현재 process_block의 호출 명령은 0개**다.
현재 분리/복원은 위의 새 MVE 매크로가 인라인으로 수행한다.
별도 helper 성능 행은 원래 helper 값이며 새 MVE 변환의 개별 성능이 아니다.

## 성능

분모/측정 범위는 비트 변환·상태 입출력·24라운드·함수 진입/복귀를 포함한
`fndsa_sha3_process_block()` 단독 호출이다. FN-DSA 전체 성능이 아니다.

| 구현 | cycles/호출 | 시간, 800 MHz | 직전 혼합형 대비 |
| --- | ---: | ---: | ---: |
| 원본 M4 ASM을 같은 M55에서 실행 | 13,382 | 16.728 µs | — |
| 직전 C9 스칼라/MVE 혼합형 | **12,521** | **15.651 µs** | 기준 |
| **현재 전체 MVE** | **17,689** | **22.111 µs** | **시간 +41.27%** |

전체 MVE는 원본 M4 ASM보다도 **32.19% 더 많은 cycles**가 걸렸다.
속도 비율로는 직전 혼합형의 0.70784×, 원본의 0.75652×다.
“41.27% 속도 향상”이나 “41.27% 처리량 감소”로 해석하면 안 된다.

새 버전 두 실행 모두 평균 17,689.00015625, 중앙값/최소 17,689,
최대 17,689.015625 cycles였다. 최대값은 한 64회 배치에 1 cycle이 추가된 경우다.
원본 재실행도 13,382.00015625였고, ELF는 이전 원본과 같은 해시다.
C9는 같은 측정 프로그램의 직전 기록이며 이번에 C9를 재빌드하지 않았다.
두 구현의 함수 시작 주소는 `0x10000844`다.

### 조건

- NUCLEO-N657X0-Q, serial `003C00223335510735383531`.
- CPU 800 MHz, ITCM 코드 / DTCM 데이터·스택, 각각 256 KiB, cache OFF.
- GCC 15.2.1, `-O3`, 기존 보드 로더·링커 배치 유지.
- 5배치 예열, 100표본 × 64회 호출, DWT, IRQ OFF, 빈 측정 루프 차감.
- 동일 입력 생성기·Keccak oracle·SHAKE 벡터·ABI 검사 프로그램.

### 성능 해석의 한계

새 구현은 상수 gather 인덱스, lane별 회전을 위한 shift 두 번과 OR,
패딩/중복 열 저장, 벡터 꼬리 처리 등이 추가된다. 기존 ROR·스칼라 tail을
벡터 명령 하나로 단순 치환한 코드가 아니다. 따라서 벡터화 범위 확대가
속도 향상을 보장하지 않았다.

이 설명은 명령·메모리 구조에 근거한다. **새 버전의 구간별 시간이나 stall별
기여도는 아직 측정하지 않았으므로 어느 요인이 몇 %의 지연 원인인지 확정하지 않는다.**
이전 16.14% / 47.73% / 34.50% 표를 현재 전체 MVE에 재사용하면 안 된다.
이 결과가 모든 전체 MVE 설계의 성능 한계를 증명하는 것도 아니다.

## 정확성·KAT·서명검증·상수시간 점검

| 검사 | 결과 |
| --- | --- |
| 독립 canonical Keccak oracle | 1,024회, 전체 25 lane 비트 일치 |
| SHAKE256 | Python hashlib 7벡터, 경계 길이·다중 블록 포함, 일치 |
| 원래 helper 회귀 | 5,120건 통과; 새 MVE 변환만의 단위 검사라는 뜻은 아님 |
| ABI | 16회, R4–R11/D8–D15 보존 |
| 키생성 KAT + NTRU 방정식 | **300/300, 불일치 0** |
| 서명 KAT + 검증·변조 거부 | **90/90, 불일치 0** |
| API 정상·비정상 입력 | **정상 64건, 비정상 3,902건 거부, failures=0, guards=0** |
| 하드웨어 | CFSR/HFSR/AFSR=0, TCM/ECC 정상 |
| 독립 라이브러리 | 기존 Makefile 빌드 통과 |

정수 비트 연산이므로 FP 근사 오차는 없다. 시험한 결과는 비트 단위 오차 0이다.
위 통과는 모든 입력의 동등성을 형식 증명한 것은 아니다.

zero/random 입력 각각 1,000회에서 zero의 raw 단일 호출 평균은
17,692.001 cycles (최소 17,692, 최대 17,693), random은 17,692 cycles였다.
Welch t는 약 1.00이었다. 두 실행에서 같은 통계를 확인했다.
검사 범위에서 큰 입력 클래스 차이는 관찰하지 않았지만 **전체 상수시간 증명은 아니다**.

[정적 감사](static_audit.json)는 실제 ELF를 읽어 다음을 확인한다.

- 조건 분기는 공개 24라운드의 `bne.w` 하나, 함수 호출 없음.
- 비벡터 메모리 접근은 ABI push/pop과 old-SP 저장/복원뿐.
- 스칼라 BIC는 SP 16바이트 정렬용 하나. 상태 데이터의 scalar XOR/rotate 없음.
- 부동소수점 산술·정수 나눗셈·간접 분기 없음.
- 공개 ρ/π gather·회전 상수표를 독립 forward 좌표 매핑과 대조.
- tail scatter 주소는 서로 겹치지 않고 내부 B 버퍼 안에 있음.
- MVE predicate는 공개 길이 1 또는 2. 주소/루프가 비밀 상태에 의존하지 않음을 수동 검토.

타이밍 검사는 제한된 표본이고 정적 감사는 완전한 taint 분석이 아니다.
전력/전자파·fault 공격 평가도 수행하지 않았다.

## 메모리·코드 크기

| 항목 | 직전 C9 | 전체 MVE |
| --- | ---: | ---: |
| 자체 최대 스택, ABI/정렬 포함 | 832 B | 1,056 B |
| process_block + 라운드 상수 | 2,164 B | 5,416 B |
| ASM 전체 `.text`, retained helpers 포함 | 3,448 B | 6,700 B |
| 추가 gather/배치 상수표 | 0 B | 896 B |

자체 최대 스택은 명령·프레임 구조로 계산한 상한이며 전체 호출 체인의 high-water 측정은 아니다.
새 프레임 944 B = A 320 + B 480 + C 64 + D 64 + 메타데이터 16.
암호 소스 해시를 비교했을 때 변경된 파일은 **sha3_cm55.s 하나**다.
외부 `Final_code/Before_slothy`는 변경하지 않았다.
