# M55_ref 기준 서명 전체 성능: 원본 / NTT / 서명 FFT / NTT+서명 FFT

측정일: 2026-09-29. 새로 만든 네 독립 소스 트리를 같은 M55 보드에서 재측정했다.

후속 측정: 같은 네 소스의 **[전체 키생성·검증 비교](result_keyverify.md)**. 서명 FFT만을 비교 요소로 유지했으며 키생성 FFT A17은 포함하지 않았다.

## 결론

**NTT+서명 FFT가 가장 빠르다. NTT를 합쳐서 서명이 느려지는 현상은 이번 동일 조건 비교에서 재현되지 않았다.**

서명 FFT만 적용한 상태에 NTT를 추가하면 서명 전체 사이클이 512에서 **2.5241%**, 1024에서 **2.5447%** 더 줄었다. 원본 대비 최종 속도는 각각 **1.5878배 / 1.6303배**다.

## 네 가지의 공통 기준 비교

배율 = 같은 크기의 원본 평균 사이클 ÷ 해당 구현 평균 사이클. 클수록 빠르다. 아래 평균은 **100회 × 2회 실행 = 200개 측정값**이며 같은 100개 서명 seed를 두 번 측정했다.

| 구현 | 512 평균 cycles | 원본 대비 배율 | 1024 평균 cycles | 원본 대비 배율 |
| --- | ---: | ---: | ---: | ---: |
| M55_ref 원본, M4 ASM ON | 17,744,081.580 | 1.0000배 | 38,034,528.755 | 1.0000배 |
| NTT만 최적화 | 17,454,703.535 | 1.0166배 | 37,425,353.750 | 1.0163배 |
| 서명 FFT 5개 함수만 최적화 | 11,464,706.490 | 1.5477배 | 23,938,668.585 | 1.5888배 |
| NTT + 서명 FFT 5개 함수 | **11,175,328.500** | **1.5878배** | **23,329,493.585** | **1.6303배** |

| 원본 대비 사이클 감소 | 512 | 1024 |
| --- | ---: | ---: |
| NTT만 | 1.6308% | 1.6016% |
| 서명 FFT만 | 35.3886% | 37.0607% |
| NTT + 서명 FFT | 37.0194% | 38.6623% |

**이 표는 전체 서명 API의 시간이다. 개별 NTT/FFT 커널의 속도 배율이 아니다.** 키생성·검증의 실행 시간도 이 표의 분모에 포함하지 않는다.

## NTT 효과를 직접 분리하면

| NTT 추가로 절약된 평균 cycles | 512 | 1024 |
| --- | ---: | ---: |
| 원본 → NTT만 | 289,378.045 | 609,175.005 |
| 서명 FFT만 → NTT+서명 FFT | 289,377.990 | 609,175.000 |

두 상황에서 절약된 **절대 사이클이 사실상 동일**하다. FFT가 빨라진 뒤에는 전체 시간이 줄어 있으므로 같은 NTT 절약량의 비율이 약 1.6%에서 약 2.5%로 커진다. 이번 입력·배치에서는 두 최적화의 이득이 거의 그대로 합산됐다.

NTT만 적용한 상태를 별도의 기준으로 삼으면, 서명 FFT 추가 효과는 512 **1.5619배**, 1024 **1.6042배**다. 이 수치는 위 표의 **M55_ref 기준 배율과 분모가 다르다.** 최적화별 배율을 단순 평균하거나 다른 기준의 배율끼리 비교하지 않는다.

이전에 제시한 서로 다른 기준의 전체 서명 배율은 `FFT만`과 `NTT+FFT`의 통제된 네 가지 비교가 아니었다. 그 숫자로 NTT의 성능 악화를 결론 낼 수 없다. 앞으로 두 최적화의 순수 효과 비교에는 이 표를 사용한다. 다만 이번 결과만으로 과거 측정의 차이가 어떤 원인 하나 때문이었다고 확정하지 않는다.

## 정확한 변경 범위

- 기준 소스: `fn-dsa_m55/M55_ref`. 원본 M4 어셈블리를 네 구현 모두 활성화하고, M55 호환 옵션도 네 독립 복사본의 `inner.h`에서 동일하게 활성화했다. 스칼라 C fallback과 비교한 것이 아니다.
- NTT: pre-SLOTHY `mqpoly_int_to_ntt()` / `mqpoly_ntt_to_int()`와 K4C RNS `mp_NTT()` / `mp_iNTT()` 및 필요한 상수표 계약. 원본 `mq_cm4.s`의 나머지 9개 함수 본문은 그대로임을 대조했다.
- 서명 FFT: `fpoly_FFT()`, `fpoly_iFFT()`, `fpoly_LDL_fft()`, `fpoly_split_fft()`, `fpoly_merge_fft()`의 채택된 native FP64 + 수동 ASM 구현. 다른 `sign_fpoly.c` 본문은 GM 심볼명·가시성 차이를 제외하고 원본과 같다.
- **키생성 FFT A17 등은 전부 제외**했다. `kgen_fxp.c`, `kgen_ntru.c`, `kgen_poly.c`, `kgen_inner.h`, `sign_core.c`, `sign_sampler.c`, `sign_fpr.c` 등은 원본이다.
- RNS NTT는 이 서명 타이머에 직접 포함되지 않는다. 서명에서는 공통 q-NTT가 키 복원 및 샘플링 결과의 정수 다항식 계산에 쓰인다.
- SLOTHY는 네 구현 모두 적용하지 않았다.
- 실제 암호 소스는 `variants/ref`, `variants/ntt_only`, `variants/fft_only`, `variants/ntt_fft`에 각각 독립적으로 있다. 비교를 위해 기존 작업 폴더의 코드를 수정하지 않았다.

## 측정 공정성·재현성

- NUCLEO-N657X0-Q, ST-Link `003C00223335510735383531`, CPU 800 MHz.
- GCC 15.2.1, 동일 Zephyr/보드 설정, `-O3`, `-mcpu=cortex-m55`, hard-float, `-mfpu=fpv5-d16`, `-ffp-contract=off`, `-fno-fast-math`.
- 코드 ITCM, 상수·데이터·스택 DTCM, I/D cache OFF, TCM 설정 `0x99`.
- 원본과 최적화 코드 크기가 달라져도 무관한 서명 코드가 이동하지 않도록 변경 영역을 동일한 크기의 슬롯에 배치했다. 소스를 외부 후보와 연결하는 알고리즘 선택 기법이 아니라 **비교 펌웨어의 메모리 배치 통제**다.
- ELF 검사 결과 변경하지 않은 함수 **246개**, 데이터·상수 심볼 **136개**의 주소·크기가 네 구현에서 일치했다. 키·서명·작업 버퍼와 스택 주소도 같다. 변경 객체 내부의 모든 오프셋까지 같다는 주장은 아니다.
- 동일한 메시지·키생성 seed·서명 seed. 각 크기에서 키 10개를 생성해 확인하고 마지막 키로 서명을 측정한다. 키생성 시간은 타이머 밖이다. 따라서 여러 키에 대한 성능 분포까지 대표하는 실험은 아니다.
- 워밍업 3회, 서명 seed 100개, 2회 반복. DWT cycle counter, 타이머 구간 IRQ OFF. 검증·출력 fingerprint·로그는 타이머 밖이며 서명 API 내부의 해시·인코딩은 포함한다.
- 실행 순서: `ref → ntt_only → fft_only → ntt_fft → ntt_fft → fft_only → ntt_only → ref`.
- 두 실행의 평균 차이는 모든 경우에서 0.02 cycle 이하였다. 이는 해당 고정 입력·배치의 반복성 확인이지 모든 입력에 대한 성능 보장은 아니다.
- 첫 원본 측정 뒤 키생성 KAT가 서명 FFT 테이블을 링크하지 않는 경우를 허용하도록 **검증용 linker assertion만** 수정했다. 네 서명 펌웨어를 다시 빌드했고 ELF SHA256이 변경되지 않았음을 확인했다. 원본 첫 실행과 마지막 실행은 같은 바이너리다.

메모리 슬롯·실제 사용량·ELF SHA256: [layout_audit.json](layout_audit.json). 소스별 원본 대비 변경·SHA256: [source_manifest.json](source_manifest.json).

## 정확성 검사

| 검사 | 결과 |
| --- | --- |
| 네 구현의 전체 서명 성능 실행 | 512/1024 각각 200회 × 4구현 = 총 1,600회 정상 검증 PASS |
| 성능 실행의 키·서명 fingerprint | 모든 실행에서 512 `9895079d`, 1024 `a020dd02` 일치 |
| 원본 서명 KAT | 구현별 90/90, 총 **360/360** 일치 |
| 서명 KAT의 정상 검증·변조 거부 | **360/360 PASS** |
| 원본 키생성 KAT | `ref` **300/300**, `ntt_only` **300/300**, 불일치 0 |
| 키생성 정수 NTRU 방정식 검사 | 두 키생성 경로 모두 PASS |
| 펌웨어 로드 대조 | 모든 실행의 로드된 section matched |
| 보드 종료 상태 | CFSR/HFSR/AFSR = 0, TCM/ECC 검사 PASS |
| 소스 불변성 | 각 실행 전후 및 최종 원본·채택 소스 해시 검사 PASS |

키생성 KAT는 두 종류의 키생성 구현에 대해 실행했다. `fft_only`의 키생성 소스는 `ref`와 같고, `ntt_fft`의 키생성 소스는 `ntt_only`와 같다. 네 조합별 서명 KAT에서는 실제 해당 조합으로 키생성부터 서명·검증까지 수행했다.

원시 로그에는 디버거 초기 연결 시 `0x34000000` 읽기 실패 메시지가 있다. 이는 실제 ITCM/DTCM 펌웨어 로드 대조 및 측정 시작 전 출력이다. 이후 section 대조·TCM 설정·완료 marker·fault register를 확인했으며 측정 중 fault로 간주해 숨긴 것이 아니다. 로그를 원형대로 보존한다.

검사 통과는 시험한 입력에 대한 결과다. 이번 작업에서 모든 입력의 동등성, 전체 상수시간성, 물리 부채널 내성을 새로 증명한 것은 아니다.
