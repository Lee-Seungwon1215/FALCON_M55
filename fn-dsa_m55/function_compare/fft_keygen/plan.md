# 키생성 FFT: native FP64 전환·최적화 계획

작성일: 2026-09-23
갱신일: 2026-09-24 — 논문 전수 검토·기법 실험·추가 조사·직접 어셈블리 구현 지침 명시

**상태: 구현·측정 완료.** 2026-09-24에 REFERENCE 11편 재검토, native-FP64
구현, 후보 비교, host/M55 검증과 최종 성능 측정을 완료했다. 기능·성능 기준은
통과했지만 입력 의존 FP64 timing이 관측되어 상수시간 배포 후보로는 보류한다.
세부 과정은 [`implementation_log.md`](implementation_log.md), 문헌별 적용 판단은
[`literature_review.md`](literature_review.md), 최종 수치는 [`result.md`](result.md)에 기록한다.

## 1. 목표와 변경 불가 조건

`fn-dsa_m55/ntt_opt`를 출발점으로, 지정한 **다섯 함수 모두**를 대상으로
M55의 하드웨어 FP64를 활용하는 구현을 만들고 최적화한다.
작업 위치는 `fn-dsa_m55/function_compare/fft_keygen`이다.

최종 성능 기준은 **`fn-dsa_m55/M55_ref`**다.
단순히 이전 FP64 실험보다 빨라졌거나 double을 사용했다는 이유만으로 성공으로 판정하지 않는다.

변경 불가 조건:

- FFT 영역의 복소수 한 개는 **실수부 double 하나 + 허수부 double 하나**로 표현한다.
- 고정소수점 상위·하위 비트를 각각 double에 저장하는 hi/lo 방식으로 돌아가지 않는다.
- FP32 여러 개 또는 여러 double을 묶어 한 실수값을 지속적으로 표현하는 방식으로 대체하지 않는다.
- 핵심 산술은 native FP64를 사용하고, 필요한 Q32 호환 보정을 적용한다.
- 원본 KAT 기대값을 바꾸거나 특정 seed에 대한 예외 처리를 넣어 불일치를 숨기지 않는다.
- 속도뿐 아니라 오차·KAT·서명검증·상수시간·메모리를 검사한다.
- 최적화 후보는 실제 소스로 구현한다. 빌드옵션이나 우회 링크로 다른 구현을 선택하지 않는다.
- C만으로 끝내지 않고, 유효한 후보에 대해 직접 작성한 어셈블리 구현도 시험한다.

성능 향상은 목표이지 사전 보장이 아니다. 원본보다 느린 경우, 정확성 문제가 남은 경우,
상수시간 조건을 만족하지 못한 경우도 그대로 기록한다.

### 1.1 추가 실행 지침 — 사용자 요청 반영

1. **다섯 함수의 구현 방법은 REFERENCE의 모든 논문을 읽은 뒤 결정한다.**
   모든 논문을 처음부터 끝까지 읽고 기법을 빠짐없이 목록화한다.
   이 연구의 표현·정확성·하드웨어 조건에 적용 가능한 모든 기법을 실제 후보로 구현하고
   측정한다. 적용할 수 없는 기법은 생략 사실과 이유를 명시한다.
   처음 제안한 방법만 시험하고 다른 문헌의 방법을 검토하지 않은 채 종료하지 않는다.

2. **실제 비교 결과에서 가장 좋은 유효 구현을 선택해 보고한다.**
   개별 기법과 유의미한 조합을 비교하고, 원본 KAT·정확성·상수시간 등 채택 조건을
   충족한 후보 중 최선의 결과를 선택한다. 성능 기준은 `M55_ref`이며,
   다섯 함수의 커널별 결과와 전체 키생성 결과를 모두 제시한다.

3. **중간에 막히면 원인을 파악하고 추가 논문과 다른 기법까지 조사·시험한다.**
   실패 구간을 분리해 재현하고 근본 원인을 추적한다. REFERENCE 자료만으로 해결되지
   않으면 우리 문제와 관련된 다른 논문·공식 자료를 찾아 원문을 확인하고,
   대안 기법을 구현해 같은 조건으로 검증·측정한다. 해결되지 않은 문제와 근거도 남긴다.

4. **빌드옵션·우회 링크가 아니라 명확한 소스와 직접 작성한 어셈블리로 최적화한다.**
   후보 선택을 빌드옵션이나 링크 연결에 숨기지 않고, 각 후보의 실제 구현을 독립적인
   로컬 소스로 관리한다. 어셈블리어를 직접 작성한 후보도 시험하며,
   필요한 일반 빌드 연결과 알고리즘을 다른 구현으로 교체하는 편법을 구분한다.
   코드 검토와 재현이 가능한 형태로 성능 개선을 시도한다.

이 지침은 아래 5~10절의 조사·구현·측정·검증 절차에 함께 적용한다.
**실수부 double 하나 + 허수부 double 하나**라는 표현 제약은 추가 문헌이나
대안 기법을 적용할 때도 변경하지 않는다.

## 3. 다섯 함수의 역할과 공통 인터페이스

| 최적화 대상 | 통일 후 역할 | 실제 적용 구간 |
|---|---|---|
| `vect_FFT()` | double 배열을 받는 FFT 호출 인터페이스. FP64 커널에 직접 연결 | 후보 검사, NTRU ④·⑤ |
| `vect_FFT_fp64()` | 실제 FP64 FFT 버터플라이와 Q32 호환 보정 수행 | 위 FFT 호출들의 계산 커널 |
| `vect_iFFT()` | double 배열을 받는 iFFT 호출 인터페이스. FP64 커널에 직접 연결 | 후보 검사, NTRU ④·⑤ |
| `vect_iFFT_fp64()` | 실제 FP64 iFFT 버터플라이·단계별 스케일링·보정 수행 | 위 iFFT 호출들의 계산 커널 |
| `vect_invnorm_fft()` | double 입력의 제곱합·역수 계산과 Q32 호환 보정 수행 | 후보 직교노름 검사 |

다섯 이름 모두 작업·검증·성능 보고 대상이다. 다만 동일한 FFT를 중복 구현하거나
한 번의 변환을 두 번 실행하는 구조는 아니다.

```text
vect_FFT(double 배열)  → vect_FFT_fp64(같은 double 배열)
vect_iFFT(double 배열) → vect_iFFT_fp64(같은 double 배열)
vect_invnorm_fft(double 입력 배열들) → double 실수값 출력
```

인터페이스와 FP64 커널 사이에는 고정소수점 변환이나 배열 복사를 넣지 않는다.
인터페이스가 단순 호출만 수행하면 큰 계산 비용은 커널에 있으므로,
두 함수의 속도 개선을 독립적인 성과로 중복 합산하지 않는다.

### 3.1 데이터 표현

FFT 영역에서는 기존 split-complex 배열 구조를 유지하는 것을 기본으로 한다.

```text
double f[n]
f[0 .. n/2-1] : 실수부
f[n/2 .. n-1] : 대응하는 허수부
```

실수 계수 다항식의 FFT 표현은 n/2개의 복소수이므로 총 n개의 double을 사용한다.
시간/계수 영역의 실수 다항식 입력·출력을 무조건 n개의 복소수로 확장하지 않는다.
`vect_invnorm_fft()`의 출력은 실수값이므로 첫 n/2개만 유효하며 허수부 저장은 필요 없다.

형식 변환용 정수 연산과 국소적인 산술 보정용 임시값은 사용할 수 있지만,
그것을 별도의 지속적인 hi/lo 또는 다중 워드 데이터 표현으로 바꾸지 않는다.

### 3.2 산술 규칙

```text
native FP64 산술 → 해당 연산에 필요한 Q32 절삭·반올림·wrap 보정
```

기준 구현에서는 원본의 twiddle 값, 복소수 계산 순서, 보정 위치를 유지한다.
twiddle을 더 높은 정밀도의 sin/cos로 새로 생성해 다른 수치 알고리즘으로 바꾸지 않는다.
iFFT의 단계별 half도 유지한다. 이 real FFT의 전체 정규화는 2/n이라는 점을 보존한다.

단일 double은 모든 64-bit Q32.32 raw 값을 정확히 표현하지 못한다.
이미 사라진 비트는 마지막 출력 보정만으로 복원할 수 없으므로,
**Q32 보정이 있다는 사실만으로 모든 입력 동등성을 주장하지 않는다.**
입력 범위·중간값 표현 가능성·원본 절삭 결과를 검증하고 불일치를 추적한다.

## 4. 변경 범위와 고정소수점 연결 경계

적용 범위:

1. `check_ortho_norm()`의 키 후보 직교노름 검사.
2. NTRU ④: `solve_NTRU_intermediate()`의 근사 k 계산에 사용되는 FFT/iFFT.
3. NTRU ⑤: `solve_NTRU_depth0()`의 최종 축소에 사용되는 FFT/iFFT.

초기 계획에서는 다섯 함수 밖의 점별 연산은 고정소수점으로 유지하려 했다. 그러나 실제
통합 시험에서 FFT 출력과 고정소수점 점별 연산 사이를 왕복하면 binary64에서 이미 사라진
Q32 하위 비트를 복구할 수 없어 NTRU solve가 반복 실패했다. 따라서 **성능 평가 대상은
여전히 다섯 함수로 고정**하되, 그 사이의 FP64 표현을 유지하기 위한 다음 지원 함수만
동일한 수치 경로로 전환했다.

- `vect_mul_fft_fp64()`, `vect_inv_mul2e_fft_fp64()`,
  `vect_div_selfadj_fft_fp64()`
- `vect_adj_fft_fp64()`, `vect_mul_realconst_fp64()`,
  `vect_mul_selfadj_fft_fp64()`, `vect_sqnorm_fp64()`
- `vect_set_fp64()`, `poly_big_to_fp64()`와 명시적인 경계 변환 함수

이 범위 확대의 목적은 새 성능 타깃을 추가하는 것이 아니라, 다섯 타깃 사이에서
`double` 표현을 보존해 정상적인 키 생성 경로를 만드는 것이다. NTT/RNS, CRT, Bezout,
정확한 정수 해 갱신과 서명 FFT·sampler·검증 코드는 변경하지 않는다.

`fxr` typedef를 전역적으로 double로 바꾸거나, 고정소수점 배열을 단순히
`double *`로 캐스팅하는 것은 금지한다. 표현 변환·작업 버퍼·데이터 수명을 명시한다.
필요한 버퍼의 RAM·스택 비용과 변환 중 정밀도 손실도 검사한다.

| 적용 후보 | 어느 함수에 어떤 방식으로 옮길지 명시 |
| 구현·측정 완료 | 실제 코드, 빌드/입력 정보, 검증·사이클 결과 |
| 실패·탈락 | 정확성·시간차·성능·메모리 등 탈락 원인 |
| 부적합 | FP32 다중 워드, NTT 전용 산술, ISA 불일치 등 구체적 이유 |
| 미해결 | 남은 문제와 다음 조사·실험 항목 |

적용 가능한 기법은 빠뜨리지 않고 후보로 시험한다. 표현 제약이나 알고리즘 조건에
맞지 않는 기법을 억지로 적용하지 않고, 적용하지 않은 이유를 남긴다.
개별 후보와 가능한 유의미한 조합을 비교하되 모든 조합이 항상 가능하다고 가정하지 않는다.
최종 선택은 **실제로 시험하고 검증한 후보 중 최선**이며 전역 최적성을 주장하지 않는다.

### 5.2 중간에 막힐 때

1. 첫 수치 불일치·비밀값 의존 시간차·성능 저하가 발생하는 최소 구간을 격리한다.
2. 표현 손실, 반올림/절삭, wrap/half, 명령 지연, 메모리 접근,
   레지스터 spill, 코드 배치, ABI/컴파일 문제를 구분한다.
3. 분리한 실제 입력으로 M55에서 재현한다.
4. 관련 추가 논문과 공식 기술 자료를 검색하고 원문을 확인한다.
5. 새로운 기법을 같은 데이터 표현 제약 안에서 구현하고 동일한 검사로 비교한다.
6. 해결하지 못한 조건은 명시하며, 범위를 넓혀야 하거나 표현 제약을 바꿔야 한다면 임의로 진행하지 않는다.

## 6. 최적화 후보와 진행 순서

아래는 현재 코드에서 도출한 초기 후보다. 문헌 전체 재검토 후 근거를 보강하고 수정한다.
아직 특정 기법의 성능 향상이나 정확성을 확인한 결과가 아니다.

### 6.1 0단계: 기준과 검증 자료 고정

- `M55_ref`와 `ntt_opt`의 원본을 보존하고 소스 hash·차이를 기록한다.
- 후보 검사·NTRU ④·⑤의 실제 입력과 중간값을 확보한다.
- 원본 함수 출력, 후보 판정, 정수 k, 키 digest를 대조 자료로 고정한다.
- 알려진 경계값·회귀 seed를 검사에 포함한다.
- 신규 FP64 코드가 없는 상태의 비교군 빌드·계측부터 검증한다.

### 6.2 1단계: 다섯 함수의 FP64 기준 구현

- double 인터페이스, 실수부/허수부 표현, 공통 FP64 보정 산술을 구현한다.
- 실제 하드웨어 FP64 명령이 생성되는지 역어셈블리로 확인한다.
- 원본 twiddle과 계산 순서, iFFT 단계별 half를 보존한다.
- 후보 검사·NTRU ④·⑤와 필요한 변환 경계를 연결한다.
- 불일치가 있으면 첫 차이를 추적한다. 단순히 이전 FP64 함수를 복사했다고 안전하다고 간주하지 않는다.

### 6.3 2단계: 공통 Q32 보정 비용 감소

- 범위와 표현 가능성이 증명되는 구간에서만 불필요한 wrap 제거.
- 동등한 결과를 보존하는 중복 보정 통합과 명령 단축.
- twiddle의 실수부·허수부 합 등 반복 상수 계산을 원본 산술 규칙으로 미리 수행.
- compiler가 이미 제거하거나 루프 밖으로 이동한 계산인지 역어셈블리로 확인.
- FMA 잔차를 이용한 보정 후보는 검토할 수 있으나, 지속적인 다중 워드 표현으로 바꾸지 않음.

곱셈 뒤 절삭을 임의로 없애거나 마지막으로 미루지 않는다.
기존 복소수 곱셈은 이미 실수 곱셈 3회 방식이므로 이를 새 개선이라고 보고하지 않는다.
FMA나 다른 복소수 곱셈 공식을 사용하면 중간 반올림이 달라질 수 있으므로 별도 수치 후보로 검사한다.

### 6.4 3단계: FFT/iFFT 구조와 메모리 접근

- 공개된 `logn`에 따른 작은 크기 경로와 일반 경로 비교.
- 2층 병합을 먼저 시험하고, 레지스터·코드 크기가 허용되면 3층 병합 검토.
- 각 층의 산술·보정 의미를 유지한 채 중간 저장/재로드와 반복문 비용 감소.
- forward의 짧은 간격 마지막 층, inverse의 짧은 간격 첫 층 전용 경로 검토.
- 상수·계수 로드 재사용, 정렬, 레지스터 보관과 spill 비용 비교.

레이어를 병합하는 것과 보정 횟수를 줄이는 것은 별도 변경이다.
iFFT의 단계별 half를 최종 스케일링 한 번으로 바꾸는 것은 수치 결과가 달라질 수 있으므로
첫 병합 후보에서는 하지 않으며, 별도 검증 없이 채택하지 않는다.

### 6.5 4단계: `vect_invnorm_fft()` 특수화

계산은 `d[i] = 2^e / (a_re² + a_im² + b_re² + b_im²)`다.

- 제곱 4개·합산·나눗셈·보정의 비용을 각각 확인한다.
- 독립 제곱과 데이터 읽기를 효율적으로 배치한다.
- 실제 후보 검사에서 사용하는 공개 인자 `e=0`의 분자 1 경로를 특수화한다.
  다른 지원 `e`에 대한 기능은 유지한다.
- 분모의 범위·부호·정상값 조건이 입증될 때만 불필요한 일반 처리를 줄인다.
- 원본 제곱·합·나눗셈의 단계별 수치 규칙과 최종 결과를 확인한다.

이 함수는 이미 출력 원소당 나눗셈 1회다. 나눗셈 두 번을 한 번으로 줄이는 다른 함수의
최적화와 혼동하지 않는다. 빠른 역수 근사 후보를 도입한다면 정확한 보정과 시간 특성을 별도 검증한다.

### 6.6 5단계: 어셈블리·명령 스케줄링·SLOTHY

- 유효한 계산·보정 커널에 대해 직접 작성한 어셈블리 후보를 시험한다.
- 독립 버터플라이 2개/4개 전개와 곱셈·덧셈·보정·load/store 순서 비교.
- 레지스터 압박, spill, ABI 보존, 스택 정렬·사용량을 검사한다.
- SLOTHY의 대상 명령·M55 모델 지원을 확인하고 가능한 루프/직선 구간에 적용한다.
- SLOTHY 출력은 검토한 실제 `.s` 소스로 보존한다. 빌드 때 몰래 다른 알고리즘을 생성하지 않는다.
- 수동 최적화 전·후와 SLOTHY 전·후를 구분해 보존하고 실제 보드에서 재검증한다.

기법별 후보 수, 구체적 레이어 조합, 새 `.s` 파일명과 하위 폴더명은 아직 확정하지 않았다.
단계 번호는 초기 실험 순서이며, 논문 재검토와 측정 근거에 따라 조정할 수 있다.

## 7. 독립적이고 명확한 구현 방식

- 각 후보는 로컬 소스로 재현 가능하게 관리한다. 원본과 후보의 실제 코드를 비교할 수 있어야 한다.
- `#define`/빌드옵션으로 알고리즘 후보를 선택하거나 다른 폴더의 구현을 include/link해 대체하지 않는다.
- 구현 차이는 C 또는 `.s` 본문에 명시한다. 다른 후보의 암호 소스에 런타임·빌드 의존성을 만들지 않는다.
- 컴파일러·ABI 설정, 정상적인 소스 목록 추가, 공통 보드 부트·링커·로더 사용은 허용한다.
  이는 알고리즘을 빌드옵션이나 우회 링크로 교체하는 것과 구분한다.
- 원본과 후보를 한 측정 프로그램에서 실행해야 한다면 로컬 복사본·명시적인 테스트 심볼로 구분하고
  어느 소스가 실제 컴파일됐는지 확인한다. 링크로 한쪽을 다른 구현으로 바꾸지 않는다.
- 계측용 소스 사본은 산술을 바꾸지 않으며, 계측 제거 후 원본 복원 여부를 확인한다.
- 공유 helper 수정이 목표 밖 함수에 전파되지 않도록 사용처를 감사한다.

## 8. 다섯 함수의 단독 커널 성능 비교

전체 키생성만 측정하고 끝내지 않는다. 다섯 함수 각각을 분리해 직접 호출하고 비교한다.

| 측정 대상 | `M55_ref`의 대응 비교군 |
|---|---|
| `vect_FFT()` | 원본 `vect_FFT()` |
| `vect_invnorm_fft()` | 원본 `vect_invnorm_fft()` |
| `vect_iFFT()` | 원본 `vect_iFFT()` |
| `vect_FFT_fp64()` | 같은 변환을 수행하는 원본 `vect_FFT()` |
| `vect_iFFT_fp64()` | 같은 변환을 수행하는 원본 `vect_iFFT()` |

`M55_ref`에는 `_fp64` 함수가 없으므로 이름이 아니라 동일한 계산 작업을 대응시킨다.
인터페이스가 커널을 호출하는 중첩 시간은 각각 보고하되 합산하지 않는다.

### 8.1 비용을 세 종류로 분리

1. **순수 커널:** 함수 실행 자체. 입력 준비·재설정·출력 검사는 타이머 밖.
2. **연결 비용 포함:** 실제 적용에 필요한 고정소수점↔double 변환과 추가 처리 포함.
3. **전체 키생성:** 실패한 후보와 NTRU 재시도를 포함한 실제 키 생성 시간.

FP64 함수끼리는 형식 변환 비용을 가상으로 추가하지 않는다.
고정소수점과 실제로 만나는 경계 비용만 포함하고, 같은 변환을 두 번 합산하지 않는다.
동일한 원본 fixture에서 각 표현의 입력을 준비하며 입력 변환에서 생긴 오차도 별도 기록한다.

### 8.2 크기와 반복

- 커널 n=512·1024를 각각 보고하고 NTRU 내부의 실제 작은 크기들도 측정한다.
- 커널 크기 n과 키 크기를 반드시 구분한다. NTRU ④는 원래 키 크기보다 작은 변환들을 사용한다.
- `vect_invnorm_fft()`는 실제 호출 크기·공개 인자 조건과 지원 경계값을 구분해서 시험한다.
- 워밍업을 측정에서 제외한 뒤 기본 100회 반복한다. 원본/후보 실행 순서를 교차해 비교한다.
- 같은 입력을 사용하되 다양한 실제 입력·경계 입력을 포함한다.
  수정되는 배열은 매 호출 전 동일 상태로 복원한다.
- 평균·최솟값·최댓값·변동을 기록하고 미세한 차이는 반복 측정으로 확인한다.

### 8.3 기본 측정 환경

기존 M55 측정 환경을 공통으로 사용하되, 실행 전에 실제 설정을 다시 검증한다.

- NUCLEO-N657X0-Q / STM32N657, CPU 800 MHz.
- mlkem-native 기반 보드 환경, 코드 ITCM / 상수·데이터·스택 DTCM, 각 256 KiB.
- cache OFF, TCM ECC ON, 성능 계측 구간 IRQ OFF, DWT cycle counter.
- GCC 15.2.1, `-O3 -mcpu=cortex-m55 -mfpu=fpv5-d16`.
- 초기에는 `-ffp-contract=off -fno-fast-math -fno-strict-aliasing` 유지.
  FMA 후보는 소스/어셈블리에 명시하고 전역 fast-math 옵션으로 대체하지 않는다.
- 원본의 의도된 어셈블리 경로를 끄지 않는다. 후보의 기존 NTT/MVE 경로도 유지한다.
- 원본과 후보에 동일한 측정 프로그램·메모리 배치 정책·입력·옵션·반복 횟수를 적용한다.
- 실행 주소·배열 주소·정렬·함수 크기를 기록한다. 작은 차이가 배치 때문인지 의심되면
  동일 실행 위치를 맞춘 대조 측정을 추가한다.
- CPU/FP 상태·TCM/ECC·fault 상태와 소스·ELF·컴파일 명령·로그 hash를 남긴다.

원본·후보에 서로 다른 환경을 적용한 기록이나 복사된 과거 로그로 새 성능을 대신하지 않는다.
상세 프로파일의 계측 영향은 대조 실행과 함께 보고하고 임의로 차감하지 않는다.

### 8.4 보고 지표

| 지표 | 정의 |
|---|---|
| 원본 cycles | 같은 조건에서 새로 측정한 `M55_ref` 대응 함수 시간 |
| 후보 cycles | 순수 커널과 연결 비용 포함 시간을 구분 |
| 속도 배수 | 원본 cycles / 후보 cycles. 1보다 크면 빠름 |
| 시간 감소율 | `(1 - 후보 cycles / 원본 cycles) × 100%`. 음수면 느림 |
| 메모리 | 코드·상수표·작업 버퍼·스택 사용량 |

후보별 표에는 함수명, 커널 n, 입력 종류, 원본/후보 사이클, 배수·감소율,
정확성·시간차 검사 상태와 원시 로그 경로를 함께 넣는다.
비교 불가능하거나 실패한 항목은 미측정/실패로 표시하고 숫자를 만들지 않는다.

전체 키생성은 `M55_ref` 대비 최종 효과와 `ntt_opt` 대비 FFT 변경의 추가 효과를 함께 본다.
기존 NTT 최적화의 이득으로 FFT의 성능 저하가 가려지지 않도록 한다.
일부 커널만 빨라졌다면 부분 성과로 보고하며 다섯 함수 모두 개선됐다고 표현하지 않는다.

## 9. 정확성·기능·상수시간 검증

### 9.1 원본 비교와 오차 추적

- 실제 키생성에서 추출한 후보 검사·NTRU ④·⑤ 입력을 원본과 후보에 동일하게 공급한다.
- 영값·작은 값·부호 혼합·큰 값·절삭/반올림 경계·wrap/half 경계 등을 검사한다.
- raw Q32 값, double 값, 필요한 절대 오차·ULP·Q32 단위 차이를 구분해 기록한다.
- FFT/iFFT 출력뿐 아니라 최종 정수 k, 후보 수락/거절, 재시도 흐름, 키 결과를 확인한다.
- 첫 차이가 발생한 연산을 단독 실행해 구현 오류와 수치 규칙 차이를 구분한다.
- 지원 입력 범위 밖 동작과 실제 허용 범위의 차이를 혼동하지 않는다.

이전 FP64 코드의 알려진 곱셈 경계값도 회귀시험에 포함한다.
예를 들어 `(1 + 2^-32) * (1 - 2^-32)`는 순수 double 곱셈과 원본 Q32 절삭이
다른 결과를 만들 수 있다. 이전 코드의 KAT 통과를 이 반례나 전체 입력 동등성의 해결로 간주하지 않는다.

### 9.2 KAT와 통합 기능

- 원본 키생성 KAT와 결과 바이트/digest를 비교한다. 기대값을 변경하지 않는다.
- NTRU 방정식과 계수 범위, 키 디코딩을 확인한다.
- 서명 KAT, 정상 서명 검증, 변조 서명 거부를 확인한다.
- 기존 불일치/guard 회귀 seed를 다시 시험하고 새로운 실패를 보존한다.
- 생성되는 키가 달라지면 후보 거부·재시도 변경인지, 산술·인코딩 차이인지 추적한다.
- 반복 실행은 같은 seed의 재시험인지 새 seed인지 구분해 집계한다.

### 9.3 상수시간과 하드웨어 확인

- 소스와 역어셈블리에서 비밀값 의존 분기·메모리 주소·반복 횟수를 확인한다.
- 공개 인자 `logn`, `e`에 따른 경로 선택과 비밀값에 따른 선택을 구분한다.
- FP64 명령과 보정 helper의 입력별 시간차, 예외값 처리, 소프트웨어 helper 호출을 검사한다.
- 실제 산술이 정수 에뮬레이션으로 되돌아가지 않고 native FP64로 수행되는지 확인한다.
- 일정 크기에서 다양한 입력군의 타이밍을 반복 측정한다.
- 키생성 자체의 후보 재시도로 생기는 시간 변화와 커널 내부의 추가 데이터 의존성을 구분한다.

유한한 KAT·시간 시험 통과만으로 모든 입력의 동등성이나 전체 상수시간을 증명했다고 쓰지 않는다.
알려진 문제를 해결하지 못했다면 그 범위와 증거를 남기고 안전한 최종 구현으로 채택하지 않는다.

## 10. 결과 관리와 완료 기준

후보마다 변경 내용·출처·판단 근거·검증 결과·원시 로그를 남긴다.
실패하거나 느려진 후보도 보존하며, 기존에 복사된 결과와 신규 결과를 명확히 구분한다.
최종 보고에는 다음을 포함한다.

- 모든 논문의 재검토 기록과 기법별 적용/미적용 사유.
- 다섯 함수의 원본 대비 커널 성능표와 필요한 변환 비용.
- 전체 키생성 성능 및 기존 NTT 개선과 FFT 추가 개선의 구분.
- 오차·KAT·서명검증·상수시간·메모리 검사 결과와 남은 한계.
- 실제 채택 소스, 직접 작성한 어셈블리, 재현 명령, 소스/ELF/로그 hash.
- SLOTHY를 적용했다면 적용 전·후 결과와 소스의 구분.
