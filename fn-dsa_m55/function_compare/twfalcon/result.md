## 스택 왕복 제거 + 레지스터 전달 (8·9단계)

2026-09-24에 두 후보를 직접 어셈블리로 구현하고, 같은 M55 펌웨어에서
기존 7단계·8단계·9단계를 함께 비교했다. **9단계를 실험 코드와 독립 통합
후보에 반영했다.** 정상 `M55_ref`, `ntt_opt`, `fft_keygen`은 변경하지 않았다.

### 무엇을 바꿨나

- **8단계:** 입력 배열 → 스택 복사와 스택 → 출력 배열 복사를 제거했다.
  산술 중간값만 저장하고 계수 배열을 직접 읽고 쓴다.
- **9단계:** twiddle 네 레지스터 상시 점유를 현재 곱셈에 필요한 두 개로
  줄였다. 남은 두 레지스터에 직전 곱셈 결과를 유지하고 바로 합성한다.
  출력 성분별로 계산·소비하여 중간 결과의 스택 왕복을 추가 제거했다.
- 각 결과를 만드는 FP32 곱셈·FMA 잔차·TwoSum·정규화의 연산 순서는 유지했다.
  이번 단계에서 저차항을 더 제거하거나 정밀도를 낮추지 않았다.
- 대상은 `ds32_bfly_fwd4_span()`, `ds32_bfly_inv4_span()`이다.
  작은 레이어의 비-span tail 함수와 C 측 패딩은 그대로다.
  채택된 FP64 invnorm도 변경하지 않았다.

| 네 butterfly 반복 1회 | 기존 7단계 | 직접 입출력 8단계 | 레지스터 전달 9단계 FFT | 9단계 iFFT |
| --- | ---: | ---: | ---: | ---: |
| 벡터 load/store 합계 | 84 | 52 | **36** | **44** |
| 커널 내부 임시 스택 접근 | 68 | 28 | **4** | **12** |
| 반복문 안 twiddle 읽기 | 0 | 0 | 8 | 8 |
| 계수 배열 접근 | 16 | 24 | 24 | 24 |
| 임시 스택 공간 | 320 B | 128 B | **32 B** | **64 B** |

주의: 현재 C 구현의 twiddle도 호출자 스택에 있으므로, 9단계의 실제
스택 주소 접근은 twiddle 8개를 합쳐 FFT **12개**, iFFT **20개**다.
표는 루프 밖 ABI 저장/복원을 제외하며, 7·8단계의 twiddle 4개 사전 읽기도
루프 밖이다. ABI 저장 96 B를 포함한 함수의 스택 사용은
416 B → 224 B → 128/160 B다. 링크 시 예약한 전체 스택 크기는 바꾸지 않았다.

실제 ELF에서 집계했다. 루프의 FP 산술 명령 수는 그대로이고, 조건 분기는
공개 block 수를 감소시키는 한 개뿐이다. 두 span 함수 코드 합계는
1,688 B → 1,432 B → **1,360 B**다.

### 동일 펌웨어 전체 FFT/iFFT 커널 비교

단위: cycles/call, 10 batches × 100 calls의 batch 평균 상위 중앙값을 반올림.
배열과 입력을 같게 사용하고 실행 순서를 번갈아 측정했다. 이는
**키 생성 API 전체가 아니라 두 실제 변환 코어**의 시간이다. 네 공개
FFT/iFFT 진입점이 공유하는 변환을 비교하며 표현 변환은 이 표에서 제외한다.

작은 span 호출까지 포함한 512/1024 전체 변환에서는 9단계가 이겼다.
이 작은 차이를 위한 크기별 분기/다른 빌드 옵션은 추가하지 않았다.

## 이전 7단계까지의 기록

### 당시 결론

요청한 `scalar tail 제거 → add/sub 결합 → 복소곱 결합 → 전체 butterfly
결합`을 모두 구현·실측했다. 전체 butterfly 결합까지 적용해도 triple-float는
Q32보다 8.13~9.73배 느렸으므로, 사전에 정한 3배 기준에 따라 `2×FP32`
double-single(`hi + lo`) MVE 구현으로 전환했다.

그 뒤 native FP64가 `M55_ref`를 이기지 못한 판정에 따라 `2×FP32`를 다시
설계했다. iFFT 최종 스케일링, twiddle 고정 span 어셈블리, 안전성이 확인된
저차항 제거를 적용한 최종 코어는 최초 `2×FP32`보다 **12.98~16.63%**
단축됐다. triple-float 초기 MVE와 비교하면 **5.00~5.24배** 빠르다.

그러나 최종 코어도 Q32 대비 **1.71~2.11배 느리고**, 입력 표현 변환까지
포함하면 **2.03~2.53배 느리다.** 전체 키 생성 KAT
300/300, 서명·검증·변조 거부 90/90, 메모리 canary, 입력 클래스별 cycle
검사는 통과했지만 `M55_ref`보다 빨라야 한다는 채택 조건은 충족하지 못했다.

따라서 `2×FP32` 전환은 **유의미한 개선 후보로 유지**한다. 그러나 아직 원본
Q32보다 느리므로 정상 펌웨어 트리에는 채택하지 않는다. 이미 채택한
`vect_invnorm_fft_fp64()`는 그대로 유지한다.

## 이전 triple-float 기준 기록

## 구현 범위

비교 대상은 다음 네 entry point에 대응하는 두 변환이다.

1. `vect_FFT()`와 `vect_FFT_fp64()`
2. `vect_iFFT()`와 `vect_iFFT_fp64()`

실수부와 허수부는 각각 `float` 3개짜리 비겹침 expansion으로 표현했다.
배열은 `re[hi, mid, lo]`, `im[hi, mid, lo]` SoA 형태이며, MVE 한 레지스터의
네 lane에는 서로 다른 복소 계수 네 개가 들어간다.

핵심 기법은 공식 TWFalcon commit
`6c3145baaced356d324ce883fe010596d08f5e75`에서 가져왔다.

- `two_sum` 기반 오차 없는 덧셈
- FMA residual을 보존하는 `two_prod`
- 네 개의 실수 곱을 쓰는 복소수 곱셈
- triple-float 정규화
- SoA 배치와 네 계수 MVE 병렬 처리
- twiddle 선계산, 연산 leaf 결합 및 수동 명령 배치

`tw32_add4_full`, `tw32_sub4_full`, `tw32_mul4_full`은 직접 작성한
MVE 어셈블리이며 실제 생성 코드에서 `vadd.f32`, `vmul.f32`, `vfma.f32`를
사용한다. 전체 복소 butterfly 하나를 단일 어셈블리 함수로 합친 것은 아니다.

주의할 점은 공식 TWFalcon이 triple-float를 **서명 경로**에 적용한다는
것이다. 키 생성의 `kgen_fxp.c` FFT에 적용한 것은 본 실험의 확장이다.

## 보드와 측정 조건

- NUCLEO-N657X0-Q, Cortex-M55
- CPU/sysclk/hclk: 800/400/200 MHz
- cache off, TCM control `0x99`, CCR `0x611`
- GCC 15.2.1, `-O3`, fast-math 및 C contraction 미사용
- DWT cycle counter
- 10 batches × 100 calls, 후보 실행 위치 AB/BA 교대
- core-only와 입력·출력 변환 포함 시간을 별도 측정

## 커널 성능

아래 값은 한 번 호출할 때의 cycle이다.

| 크기 | 변환 | Q32.32 | 기존 FP64 | TWFalcon scalar | FP32/MVE | MVE 대 scalar | MVE 대 Q32 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 512 | FFT | 115,427 | 230,662 | 1,890,602 | 1,234,492 | 34.70% 개선 | 10.69배 느림 |
| 512 | iFFT | 140,281 | 319,455 | 1,923,187 | 1,261,929 | 34.38% 개선 | 9.00배 느림 |
| 1024 | FFT | 256,511 | 508,110 | 4,236,343 | 2,718,938 | 35.82% 개선 | 10.60배 느림 |
| 1024 | iFFT | 312,344 | 707,746 | 4,308,854 | 2,781,185 | 35.45% 개선 | 8.90배 느림 |

입력·출력 표현 변환까지 포함한 비교는 다음과 같다.

| 크기 | 변환 | Q32.32 | FP32/MVE | 배율 |
| --- | --- | ---: | ---: | ---: |
| 512 | FFT | 117,266 | 1,298,491 | 11.07배 느림 |
| 512 | iFFT | 142,120 | 1,325,978 | 9.33배 느림 |
| 1024 | FFT | 260,142 | 2,846,987 | 10.94배 느림 |
| 1024 | iFFT | 315,975 | 2,909,184 | 9.21배 느림 |

MVE가 scalar triple-float를 약 35% 줄이는 데는 성공했지만, 복소 계수 하나에
FP32 성분 여섯 개가 필요하고 각 butterfly마다 오차항 계산과 정규화를 여러
번 수행한다. M55 MVE는 FP32를 네 lane 처리할 수 있어도 이 추가 연산량을
원래의 단일 `uint64_t` Q32.32 경로보다 낮추지는 못했다.

## 정확성

- primitive 8,000건: add/mul/complex-mul 모두 공식 scalar oracle과 일치
- logn 2~10 FFT: MVE와 scalar oracle의 최대 차이 1 Q32 LSB
- 원본 Q32.32 FFT와 최대 차이 141 Q32 LSB
- FFT→iFFT round-trip 최대 차이 3,992 Q32 LSB
- host의 엄격한 Q32 동등성 gate(`roundtrip <= 4 LSB`)는 실패
  (`fft=138 LSB`, `roundtrip=3,769 LSB`)
- 중간 FFT 배열은 Q32.32와 비트 동일하지 않음
- 그러나 최종 키 생성 결과는 300개 KAT 모두 동일

즉, 중간 표현까지 Q32.32와 동일한 구현은 아니지만 시험한 전체 키 생성에서
반올림 후 최종 키에 영향을 주지는 않았다.

## 상수시간 검사

어셈블리 커널의 명령 흐름에는 입력값을 조건으로 하는 분기가 없고 호출 수도
고정이다. 하지만 네 입력 클래스의 보드 cycle은 동일하지 않았다.

| 크기 | 변환 | 최소 class 평균 | 최대 class 평균 | 차이 |
| --- | --- | ---: | ---: | ---: |
| 512 | FFT | 1,234,484 | 1,237,556 | 3,072 cycles |
| 512 | iFFT | 1,261,919 | 1,263,455 | 1,536 cycles |
| 1024 | FFT | 2,718,929 | 2,725,074 | 6,145 cycles |
| 1024 | iFFT | 2,781,175 | 2,784,247 | 3,072 cycles |

FP32 flush-to-zero/default-NaN을 켜도 차이는 그대로 남았다.
따라서 소스 수준의 고정 흐름은 확인했지만, 이 결과만으로 데이터 독립적인
실행 시간을 주장할 수 없으며 **constant-time acceptance는 실패**로 기록한다.
