# 통합 키 생성에서 이득이 상쇄된 원인

2026-09-26 KST. 연결된 NUCLEO-N657X0-Q에서 동일 KAT 입력으로 확인했다.

**결론: 앞선 전체 키 생성 회귀에는 코드 배치 영향이 크게 섞여 있었다.**
수정하지 않은 정수 루틴들의 실행 위치가 달라지면서 CRT·Bezout 등이
느려졌다. 정수 루틴 8개의 주소를 양쪽에서 동일하게 맞추자 이 차이가
거의 사라졌다. 구간별 계측을 제거한 최종 대조에서도 현재 통합 후보는
M55_ref보다 키 생성 시간이 **512 4.14%, 1024 4.17% 감소**했다.

단, 이 대조는 **진단용 배치 제어**다. 기본 통합 펌웨어와 최종 ref는
교체하지 않았으며, 암호 계산 소스나 어셈블리 명령은 이번에 최적화하지 않았다.
또한 이 배속은 이전 NTT 최적화와 FFT/주변 FP64 변경을 모두 포함한다.
다섯 함수만의 독립적인 전체 키 생성 기여율이 아니다.

## 1. 전체 키 생성 무계측 대조

같은 `board_keygen_perf.c`, test0..test99 100개/크기, warmup 3회 제외.
단위는 cycles/key의 산술평균. 여기서 무계측은 **내부 구간별 타이머 없음**을
뜻하며, 전체 API 입출구의 타이머는 있다.

| 배치 조건 | n | M55_ref | 현재 후보 | 기준/현재 배속 | 현재 시간 변화 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 기존 일반 배치 (앞선 1차) | 512 | 62,738,244.21 | 67,135,489.33 | 0.9345× | +7.01% 느림 |
| 기존 일반 배치 (앞선 1차) | 1024 | 261,716,430.11 | 285,653,015.91 | 0.9162× | +9.15% 느림 |
| **정수 코드 동일 주소** | **512** | **62,738,244.17** | **60,138,543.80** | **1.0432×** | **4.14% 감소** |
| **정수 코드 동일 주소** | **1024** | **261,716,429.84** | **250,808,606.83** | **1.0435×** | **4.17% 감소** |

기준 구현의 시간은 사실상 그대로이고, 현재 후보에서 배치 영향이 제거됐다.
새 조건에서 512·1024 각각 **100/100개의 입력이 기준보다 빨랐다**.
기존 일반 배치의 수치가 측정 오류였다는 뜻은 아니다. 그 수치를 FFT 변경만의
순수 효과로 해석할 수 없다는 뜻이다. 새 대조는 100개 입력을 한 번씩 측정했고,
기존 일반 배치는 앞선 순서 반전 반복에서도 재현됐다.

## 2. 가장 큰 원인: 변경하지 않은 정수 루틴의 코드 위치

`kgen_zint31.c`는 두 소스 트리에서 SHA-256이 같다. 같은 컴파일러·옵션으로
빌드했지만, 통합 이미지에서는 해당 루틴이 뒤쪽 주소로 이동했다.

| 함수 | 기존 M55_ref 주소 | 기존 현재 후보 주소 | 진단 대조의 양쪽 주소 |
| --- | --- | --- | --- |
| `zint_rebuild_CRT()` | 0x10008f8c | 0x10010758 | **0x10000778** |
| `zint_bezout()` | 0x100093d0 | 0x10010b9c | **0x10000bbc** |

CRT/Bezout을 포함한 정수 루틴 8개를 일반 text보다 먼저 배치했다.
두 ELF에서 해당 루틴의 주소·크기가 모두 같고, **각 구현의 배치 변경 전후
모든 DTCM 심볼 주소·크기는 그대로**임을 확인했다. 데이터·버퍼·스택을
옮겨서 만든 효과가 아니다. 정수 코드를 재배치하면서 다른 코드 주소도
함께 이동하므로, 전체 시간 변화 전부를 CRT/Bezout 두 함수만에 귀속하지는 않는다.

아래는 내부 계측 결과다. CRT는 직접 분리한 deepest/FG/intermediate 호출의
합이며, `I_update` 내부에 포함된 CRT는 이 행에 다시 더하지 않는다.

| n | 정수 구간 | 기준 | 현재: 기존 배치 | 현재: 동일 주소 배치 |
| ---: | --- | ---: | ---: | ---: |
| 512 | CRT | 6,066,669 | 8,153,501 | **6,066,851** |
| 512 | Bezout | 9,994,903 | 12,969,479 | **9,995,759** |
| 1024 | CRT | 28,817,094 | 38,729,820 | **28,817,429** |
| 1024 | Bezout | 52,400,124 | 67,767,063 | **52,402,190** |

기존 배치에서 CRT는 약 34%, Bezout은 약 29~30% 느렸지만, 같은 주소로
옮긴 뒤에는 차이가 각각 0.01% 미만으로 줄었다. **코드 배치가 지연에 영향을
미친다는 것은 대조로 확인했다.** 다만 특정 ITCM 경계·명령 인출 단계·칩 내부
회로 중 어느 메커니즘인지는 이번 실험으로 확정하지 않았다.

## 3. 실제로 남아 있는 연산 비용

배치 문제와 별개로 다음 비용은 남는다. 아래 값은 기존 배치의 상세 프로파일을
같은 입력끼리 뺀 값이며, 단위는 **백만 cycles/key**다. 양수는 추가 비용,
음수는 절감이다. 구간별 타이머가 있으므로 무계측 총 시간과 정확히 같지는 않다.

| 항목 | 512 Δ | 1024 Δ | 해석 |
| --- | ---: | ---: | --- |
| CRT·Bezout (위 직접 계측 구간) | +5.061 | +25.280 | 배치 제어 시 거의 해소 |
| 주변 점별 곱셈·상수 곱·제곱합 | **+4.607** | **+16.641** | Q32 호환 FP64 보정 비용 |
| 모든 크기의 FFT+iFFT 합계 | **+1.082** | **+1.298** | 큰 크기는 이득, 작은 크기의 손해가 더 큼 |
| 입력 변환·정수 반올림/안전 검사 | +0.932 | +2.388 | 기존 고정소수점보다 추가 연산 |
| 채택한 FP64 invnorm | **−2.721** | **−12.188** | 실제 통합 호출에서도 큰 이득 |

이 표는 주요 원인만 발췌했으며 합계표가 아니다. NTT를 포함한 정수 갱신,
나눗셈 등의 다른 절감 항목은 원시 상세 보고서의 100% 표에 있다.

### 3-A. 작은 FFT에서 손해

현재 `ds32_fft_mve()`/`ds32_ifft_mve()`의 그룹 간 패킹은 `logn >= 4`에서
사용된다. n=4·8은 패딩·임시 저장을 사용하는 tail 경로이고, 공개 함수의
double↔2×FP32 변환 비용도 붙는다. n=2는 butterfly가 없어도 변환/호출
비용이 발생한다.

- n=4·8 FFT: 원본 대비 호출당 약 **4.15~4.19배 시간**.
- n=4·8 iFFT: 약 **3.88~4.15배 시간**.
- 이 배율에는 동일 방식의 타이머 비용도 포함되므로 순수 명령 비용의 배율은 아니다.
- 키 512 생성 100개에서 n=2 FFT는 46,375회, n=4는 약 21,900회,
  n=8은 약 10,960회 호출된다. 키 1024에서는 각각 약 141,860/58,540/24,800회다.
- 따라서 512·1024 크기 커널의 개선만으로 모든 실제 FFT 호출의 개선을
  대표할 수 없다. 전체 크기를 합치면 FFT+iFFT 자체는 아직 순손해다.

### 3-B. invnorm 주변의 Q32 보정 비용

느려진 함수는 다섯 목표 함수 외의 통합 지원 함수다.

| 함수/구간 | 통합 누적 시간: 원본 대비 |
| --- | ---: |
| `vect_mul_fft_fp64()` | 약 **5.5~5.6배** |
| `vect_mul_realconst_fp64()` | 약 **8.6배** |
| `vect_mul_selfadj_fft_fp64()` | 약 **10.4배** |
| `vect_sqnorm_fp64()` | 약 **9.9배** |

`fp64q_mul()`은 단순 FP64 곱셈이 아니라 Q32 스케일 조정 → 곱셈 → floor →
범위 보정까지 수행한다. 복소곱과 제곱합은 이를 반복한다.
반대로 채택한 invnorm은 양의 정상 분모·e=0에 특화된 역수 경로여서 빠르다.
즉 같은 부동소수점 연산이라고 비용이 같지 않다.

후보 검사에서 invnorm이 절감한 **2.721 / 12.188 Mcycles** 중 주변 상수 곱·
selfadj 곱·제곱합이 **2.549 / 11.418 Mcycles**를 다시 사용한다.
이 때문에 invnorm 약 7.24배 개선이 후보 검사 전체의 7배 개선으로 이어지지 않는다.

## 4. 재시도·정확성·계측 영향

- 같은 100개 seed에서 NTRU 시도 횟수는 양쪽 모두 키 512에서 127회,
  키 1024에서 173회다. 성공은 각각 100회. 후보 샘플링/검사 횟수도 같다.
  전체 손해가 단순히 재시도 증가 때문에 발생한 것은 아니다.
- 실패 후보 내부의 일부 축소 반복 수는 안전 검사 때문에 조금 다르다.
  모든 중간값·모든 내부 반복이 동일하다는 주장은 하지 않는다.
- 최종 무계측 동일 주소 대조: 각 구현 KAT·정확한 NTRU 방정식 **200/200 PASS**,
  인코딩된 비밀키+공개키 해시 **200/200쌍 일치**. 기존 실행의 키와도 같다.
- 상세 프로파일도 각 구현 KAT·NTRU 검사를 통과했고 생성된 키가 같았다.
- 일반 배치 상세 프로파일의 전체 시간 증가는 기준 1.31~2.01%, 현재 1.84~2.70%.
  정확한 전체 배속은 1절의 내부 무계측 대조를 사용한다. 타이머 비용 임의 차감 없음.
- 코드 ITCM·데이터/상수/스택 DTCM 각 256 KiB, 캐시 OFF, 800 MHz,
  GCC 15.2.1 -O3, 같은 FP 설정·IRQ ON·64-bit SysTick 계측.
- 새 서명 KAT나 전체 상수시간 증명을 수행한 것은 아니다. 이번 작업은
  소스 변경 없는 성능 원인 진단이다.

## 5. 다음 우선순위와 변경 범위

1. 다음 성능 비교에서는 변경하지 않은 공통 정수 루틴의 배치 영향부터 통제한다.
2. FFT 범위에서는 n=2·4·8의 전용 경로와 표현 변환 비용이 우선이다.
3. 통합 지원 함수의 일반 Q32 보정을 입력 범위에 맞게 줄일 여지를 별도로 검토한다.
   KAT와 범위/상수시간 검토 없이 보정이나 안전 검사를 제거하면 안 된다.

이번에는 **측정 코드·진단용 빌드 설정·보고서만 추가/수정**했다.
`M55_ref`, 현재 후보의 암호 C/어셈블리 본체, `ntt_opt` 및 최종 ref는 수정하지 않았다.
진단용 코드 배치를 최종 구현으로 자동 채택하지 않았다.
