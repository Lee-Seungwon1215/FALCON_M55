# 전체 키 생성: M55_ref와 현재 통합 후보 재측정

> 후속 진단: 아래 일반 배치 결과에는 공통 정수 코드의 실행 위치 차이가
> 섞여 있었다. 정수 코드 주소를 맞춘 별도 무계측 대조에서는 4.14% / 4.17%
> 개선됐다. 기본 통합 구현을 교체한 것은 아니다. [원인과 대조 결과](integration_diagnosis.md).

2026-09-26 KST. **현재 후보의 전체 키 생성은 M55_ref보다 느리다.**
512에서는 7.01%, 1024에서는 9.15% 시간이 더 걸렸다. 실행 순서를
뒤집어 다시 측정해도 같은 결론이었다. 암호 구현은 이번에 변경하지 않았다.

## 최종 결과

같은 100개 seed를 각 크기·구현에서 두 번씩 측정한 산술평균이다.
총 200개 측정값/크기/구현이며, 서로 다른 seed가 200개인 것은 아니다.

| n | M55_ref 평균 cycles | 현재 평균 cycles | M55_ref 평균 ms | 현재 평균 ms | 배속: 기준/현재 | 시간 증가 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 512 | 62,738,244.125 | 67,135,489.315 | 78.423 | 83.919 | **0.9345×** | **7.0089%** |
| 1024 | 261,716,429.945 | 285,653,014.280 | 327.146 | 357.066 | **0.9162×** | **9.1460%** |

배속은 `Σ 기준 cycles / Σ 현재 cycles`다. 1보다 작으면 느린 것이다.
시간으로 표현하면 현재 후보가 각각 **1.0701배 / 1.0915배** 걸린다.
개별 seed의 배속을 단순평균한 값은 아니다.

## 반복 확인

| 회차 및 순서 | n | 기준 평균 cycles | 현재 평균 cycles | 현재 시간 증가 |
| --- | ---: | ---: | ---: | ---: |
| 1: 기준 → 현재 | 512 | 62,738,244.21 | 67,135,489.33 | 7.008875% |
| 2: 현재 → 기준 | 512 | 62,738,244.04 | 67,135,489.30 | 7.008875% |
| 1: 기준 → 현재 | 1024 | 261,716,430.11 | 285,653,015.91 | 9.146000% |
| 2: 현재 → 기준 | 1024 | 261,716,429.78 | 285,653,012.65 | 9.145999% |

각 구현의 두 회차 평균 차이는 0.000002% 미만이었다. 두 회차·두 크기
모두 현재 후보가 빨라진 seed는 0/100개였다. 이 재현성은 시험한 입력과
배치 조건에 대한 것이며, 모든 seed나 모든 코드 배치를 보장하지 않는다.

## 비교 대상과 측정 범위

- 기준: `fn-dsa_m55/M55_ref` 자체를 빌드. 기존 M4 어셈블리 ON,
  M55 호환 모드 ON. 어셈블리를 꺼서 느리게 만든 C 기준이 아니다.
- 현재: `fn-dsa_m55/function_compare/twfalcon/integration_candidate` 자체를 빌드.
  11단계 사전 변환 상수표, 2×FP32 MVE FFT, FP64 invnorm 및 이전 NTT
  최적화와 주변 FP64/Q32 경로를 포함한다. **FFT만 바꾼 대조 실험은 아니다.**
- 동일한 `validation/board_keygen_perf.c`로 `fndsa_keygen_seeded_temp()`
  전체를 계측. PRNG 처리, 모든 후보 거부·재시도, NTRU solve,
  공개키 계산, 비밀키·공개키 인코딩을 포함한다.
- 원본 KAT의 `test0`..`test99`를 512·1024 각각 사용. 각 크기·회차에서
  warmup 3회는 제외했다. seed 문자열 생성, 출력 해시, KAT·NTRU 검사와
  로그 출력은 계측 밖이다.

## 동일하게 맞춘 환경

- 연결된 NUCLEO-N657X0-Q, CPU 800 MHz, 캐시 OFF.
- 코드 ITCM, 데이터·상수·작업 버퍼·스택 DTCM. 각각 256 KiB.
- GCC 15.2.1, `-O3`, `-mcpu=cortex-m55`, `-mfpu=fpv5-d16`,
  `-ffp-contract=off`, `-fno-fast-math`. 두 구현 모두 M4 ASM/M55 호환 ON.
  현재 구현의 RNS MVE 연결에만 `FNDSA_MVE_MP31=1`이 들어가는 것은
  비교 대상 구현 자체의 차이다.
- 동일한 Zephyr 설정 및 생성된 링커 스크립트 SHA-256 확인.
  별도 펌웨어이므로 **배치 정책은 같지만 함수의 세부 주소는 같지 않다.**
- 긴 키 생성 호출은 `k_cycle_get_64()`의 64-bit SysTick 계수로 측정.
  두 구현 모두 인터럽트 ON이며 짧은 시스템 tick 처리 비용도 포함한다.
  이전 FFT 커널 IRQ OFF 측정과 수치·분모를 섞지 않았다.
- 보드 상태: cpu/cycle_hz=800000000, FPSCR=0x00040000,
  CCR=0x00000611, TCM_CONTROL=0x99. CFSR/HFSR/AFSR=0,
  TCM/ECC 검사 PASS.

| 펌웨어 | ITCM 사용량 | DTCM 사용량 (예약 스택 포함) |
| --- | ---: | ---: |
| 기준 | 76,752 B | 179,752 B |
| 현재 | 110,852 B | 208,552 B |

## 정확성 확인

- 각 구현·회차: 원본 KAT 및 정확한 NTRU 방정식 검사 **200/200 PASS**.
  두 회차 합계 각 구현 400/400 PASS (서로 다른 입력은 200개).
- 기준/현재의 인코딩된 비밀키+공개키 SHA-256은 각 회차 **200/200쌍 일치**,
  두 회차 합계 400/400쌍 일치.
- 두 회차에서 각 구현의 ELF와 소스 해시가 그대로임을 확인했다.
- 서명·검증 및 상수시간 실험은 이번 전체 키 생성 성능 측정에서 다시
  수행한 항목이 아니다. 기존 결과는 이 단계의 README에 별도로 보존했다.

## FFT 커널 개선과 왜 구분해야 하나

앞선 n=512·1024 FFT/iFFT 커널은 M55_ref 함수보다 1.10~1.20배 빨랐다.
그러나 이 수치를 **전체 키 생성 배속**으로 옮겨 말하면 안 된다.
NTRU solve는 축소된 여러 크기의 FFT도 호출하고, 현재 통합 후보에는
입력 변환·점별 연산·반올림 등 다른 구현 변경도 포함되어 있다.

이번 결과로 **전체 키 생성 성능 목표는 아직 달성하지 못했음**을 확인했다.
어느 구간이 이 손해를 만드는지는 이번 전체 타이머만으로 확정할 수 없다.
확정하려면 같은 입력에서 크기별 FFT 누적 시간과 주변 FP64/Q32 경로를
추가 분리 계측해야 한다. 이번 요청에서는 구현 교체나 추가 최적화는 하지 않았다.
