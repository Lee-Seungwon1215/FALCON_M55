# 단일-double Q32 보정 후보의 추가 검증

> 수정된 본체의 새 성능·실제 키생성 중 근사 k 연산비중은
> [performance_profile_result.md](performance_profile_result.md)에 기록했다.
> 아래는 원인 추적·guard 수정 이전의 역사적 결과다.

> **후속 본체 수정 완료:** 아래 5개 실제 키 불일치는 안전 guard를 수정한
> 본체에서 모두 해결됐다. M55 전체 키생성·서명 KAT와 호스트 20,000개도
> 재검사했다. 최신 기록은 [guard_integration_result.md](guard_integration_result.md).
> 아래 성능 수치는 수정 전 소스의 측정이다. 이번 guard 수정은 성능·상수시간
> 문제를 다루지 않았으며 새 성능 측정값으로 대체한 것도 아니다.

2026-09-23 수정 전 기록. **당시 결론: `q32_trial`은 원본을 대체하는 최적화로 채택할 수 없다.**
암호 구현을 더 수정하지 않고, 원본 동등성·커널 성능·입력별 시간을 확대 검사했다.
기존 KAT 통과를 취소하거나 기대값을 변경한 것이 아니라, 추가 시험에서
새로운 실패를 확인한 것이다. 기존 연구 ref는 변경하지 않았다.

> 후속 원인 추적: 5개 실제 키 불일치의 직접 원인은 다른 k가 아니라
> 추가 안전 검사의 과도한 거부였다. 검사 상한을 재설계한 진단용 사본은
> 20,000키와 기존 host KAT를 통과했다. 당시에는 본체가 미반영이었으며,
> 이후 본체 반영은 위 최신 보고서에서 확인한다. 성능·상수시간 문제는 미해결이다.
> 자세한 구분은 [failure_trace_result.md](failure_trace_result.md)에 있다.

## 1. 정확성·동등성

| 검사 | 결과 |
|---|---|
| 기존 M55 원본 키생성 KAT | 이전 기록 300/300, 이번 암호 소스 변경 없음 |
| 추가 host seed, 512 각 10,000개 | **9,998개 일치 / 2개 불일치** |
| 추가 host seed, 1024 각 10,000개 | **9,997개 일치 / 3개 불일치** |
| 위 5개를 M55에서 원본·후보 각각 재현 | **5개 모두 host와 같은 서로 다른 키 digest** |
| 추가 host 전체의 NTRU 식·계수 범위 | 두 구현 모두 20,000/20,000 PASS |
| 위 5개 M55 키로 서명·정상 검증·변조 거부 | 원본 5/5, 후보 5/5 PASS |
| 추가 frozen 실제 NTRU 입력 19개, 최종 k | 19/19 일치, 원본 fixture 검사도 PASS |
| 곱셈 및 후속 반올림의 경계값 반례 | host와 M55 모두 같은 불일치 재현 |

seed 문자열은 `fp64-audit-20260923-<index>`, index=1000..10999이다.
이전 0..999 범위 2,000개와 겹치지 않는다. sk||pk의 SHA-256 digest를 비교했다.
불일치: 512의 **1198, 7470**, 1024의 **1691, 4395, 10491**.
이들은 upstream에 실린 KAT 벡터가 아니라 새로 추가한 결정적 회귀시험 입력이다.
발견한 5/20,000 비율을 임의 seed 전체의 실패 확률로 해석하지 않는다.

즉, **유효한 키/서명을 만든다**는 것과 **같은 seed에서 원본과 같은 키를
만든다**는 것은 별개의 조건이다. 후자는 이번 추가 시험에서 실패했다.

### 정확히 계산할 수 있는 작은 반례

두 입력 모두 double에 정확히 들어간다.

```text
x = 1 + 2^-32
y = 1 - 2^-32
정확한 곱 = 1 - 2^-64

원본 fxr_mul: Q32.32 절삭 → 1 - 2^-32  (raw 0x00000000ffffffff)
fp64q_mul:   double 곱에서 이미 1로 반올림 → Q32 절삭을 해도 1

각 결과에서 0.5를 빼고 정수 반올림:
원본 k = 0, 후보 k = 1
```

이 반례는 실수부/허수부 사이 캐리 누락이 아니라 **double 곱의 반올림 뒤에
Q32 절삭을 적용하는 순서**의 문제다. 보정 이전에 사라진 곱의 하위 정보를
나중에 `floor`만 적용해 되찾을 수 없다. 보드에서도 정확히 같은 결과를 확인했다.
이 작은 연산 조합이 위 5개 실제 키 생성의 최초 분기 지점이라고까지 확인한
것은 아니다. 이 보고서 이후 그 5개의 첫 차이를 추적했고, 키가 달라지는 직접
원인은 추가 guard의 조기 거부로 확인했다. 위의 후속 원인 보고서를 참고한다.

## 2. 커널 성능

실제 NTRU 중간 상태 19개(logn=1..9, 차수별 일반 상태와 큰 k 상태 각각 1개,
추가 불일치 진단 상태 1개)를 사용했다. 한 ELF 안에서 원본 fixed와 후보를
**동일한 배열 주소**에 넣어 순서를 번갈아 호출했다. 각 10회 준비 실행 후 100회.
입력 복원·변환·출력은 계측에서 제외하고 DWT 사이클을 측정했다.

- NUCLEO-N657X0-Q, CPU 800 MHz, cache OFF.
- ITCM 코드 / DTCM 데이터·상수·스택, 각각 256 KiB 설정.
- GCC 15.2.1, `-O3 -mfpu=fpv5-d16 -ffp-contract=off -fno-fast-math`.
- 원본 fixed의 M4 정수 inline ASM 활성화, 같은 소스 파일에 들어 있는 함수끼리 비교.
- 원본/후보의 함수 주소는 서로 다르며 강제로 같은 주소에 재배치하지 않았다.
  데이터 주소·환경·입력·측정 호출 방식은 동일하다.

아래는 차수별 두 실제 입력의 평균. **비율=후보 시간/원본 시간**이며
1보다 크면 느리다. FFT 크기는 키의 차수가 아니라 해당 재귀 단계의 배열 크기다.
현재 대상 ④에서 키 512의 최대 FFT 크기는 256, 키 1024는 512다.

| 커널 | FFT 크기 | 원본 cycles | 후보 cycles | 후보/원본 |
|---|---:|---:|---:|---:|
| FFT | 256 | 55,925 | 940,385 | **16.82배 시간** |
| FFT | 512 | 126,039 | 2,141,800 | **16.99배 시간** |
| iFFT | 256 | 63,752 | 1,412,189 | **22.15배 시간** |
| iFFT | 512 | 143,334 | 3,220,731 | **22.47배 시간** |
| 점별 복소 곱셈 | 256 | 8,756 | 201,954 | 23.06배 시간 |
| 점별 복소 곱셈 | 512 | 17,460 | 403,810 | 23.13배 시간 |
| 제곱합·역수 준비 | 256 | 454,574 | 270,796 | **0.596배, 약 40.43% 감소** |
| 제곱합·역수 준비 | 512 | 909,102 | 541,588 | **0.596배, 약 40.43% 감소** |
| 반복부 FFT→점곱→iFFT→k | 256 | 130,653 | 2,567,835 | 19.65배 시간 |
| 반복부 FFT→점곱→iFFT→k | 512 | 291,293 | 5,792,984 | 19.89배 시간 |
| 준비+반복 1회 | 256 | 641,130 | 3,778,994 | 5.89배 시간 |
| 준비+반복 1회 | 512 | 1,326,412 | 8,476,350 | 6.39배 시간 |

「준비+반복 1회」는 f FFT→역수 준비→F FFT→점곱→iFFT→k이다.
정수 입력 추출·RNS/CRT·해 갱신·반복 횟수 등은 포함하지 않는다.
**이 비율을 전체 키 생성이나 전체 NTRU solve의 지연 비율로 사용하면 안 된다.**

역수 준비는 빨라졌지만 자주 실행하는 FFT·iFFT의 보정 비용이 크다.
ELF에는 실제 `vmul.f64`, `vadd.f64` 등이 있고 `__aeabi_d*` helper는 없다.
즉 소프트웨어 double 때문이 아니라, FP 연산마다 반복되는 비트 추출·floor·wrap
등의 비용이 포함된 결과다. 이 측정은 hi/lo 두-double/성분 구현의 옛 수치가 아니다.

독립 커널 iFFT·점곱·역수의 입력은 원본 계산에서 얻은 동일 수치를 공유했고,
합성 준비·반복·pipeline은 각 구현의 중간값을 이어서 사용했다. 공개 입력 크기만
같은 임의 배열을 한 번 측정해 실제 NTRU 구간이라고 표현한 것이 아니다.
다만 frozen 상태는 제한된 표본이므로 모든 실행의 성능 분포를 대표하지 않는다.

## 3. 상수시간: 현재 빌드 FAIL

소스에 명시적인 `if`가 없다고 실행 파일도 분기 없는 것은 아니다.
GCC가 `fp64q_floor`의 마스크 연산을 지수값에 따른 조건 분기로 바꿨다.
동일 ELF의 `probe_floor`에서 입력 double의 지수를 `ubfx`로 추출하고,
`0x10007a20`의 `beq`, `0x10007a78`의 `cbz`로 다른 경로를 간다.
실제 `fndsa_vect_FFT_fp64` 안에도 같은 형태가 인라인되어 있다
(예: 지수 추출 `0x10000406`, 조건 분기 `0x10000436`).

8개 helper × 12개 입력 종류를 고정 길이 128회 묶음으로 측정했다.
입력 순서는 각 회전마다 바꾸고, 5회 준비 후 50회 기록했다. 타이머·호출·sink
저장 오버헤드는 포함하지만 두 입력 클래스에서 같으며, 아래 차이는 그대로 남는다.

| 측정 | 입력 A | 입력 B | A cycles | B cycles |
|---|---|---|---:|---:|
| floor, 128회 | 0.25 | 1 | 16,400 | 17,168 |
| 보정 나눗셈, 128회 | x=2^-32, y=1.5 | x=1, y=1.5 | 76,048 | 78,736 |
| 후보 FFT, n=256 | 모든 계수 ±2^-32 교대 | 모든 계수 1 | 918,652 | 940,388 |
| 원본 FFT, n=256 | 같은 ±2^-32 교대 | 같은 1 | 55,864 | 55,864 |

각 표의 클래스 안에서는 50회 min=max였다. **정상 범위의 유한 입력**으로도
시간 차이가 나므로 NaN·Inf·서브노멀 등의 범위 밖 입력에만 생기는 문제가 아니다.
원본의 이 표본에서 차이가 없다는 사실 역시 원본 전체의 상수시간 증명은 아니다.

동일 ELF를 보드에 다시 올려 독립 실행한 두 번째 측정에서도 성능 기록
266줄과 FFT 입력별 타이밍 기록 72줄은 모두 동일했다. helper 기록 96줄 중
4줄에서 128회 묶음 50회 중 한 번의 1-cycle 변동만 있었고, 위 입력 간 시간
차이와 판정은 재현됐다. 모든 primitive 실행이 잡음 없이 동일했다고 주장하지 않는다.

이것은 모든 FN-DSA 함수를 형식 검증한 결과가 아니다. 그러나 바꾼 FFT 경로
자체에서 입력 의존 분기와 시간 차이를 찾았으므로 **전체가 상수시간이라고
승인할 수 없는 충분한 실패 근거**다. 고정 logn에서의 변경 커널을 검사했으며,
원래 키 생성의 후보 재시도/종료까지 항상 같은 시간이라는 전제도 두지 않았다.
전력/EM 분석, 공격 가능성·비밀 복구 실증, 모든 메모리 접근의 형식 증명은 하지 않았다.

## 4. 판단과 다음 수정 범위

1. 기존 300개 KAT 성공은 제한된 회귀시험 성공으로 남긴다. 일반 동등성 주장은
   이번 실제 seed 반례로 성립하지 않는다.
2. 현 후보에는 보정 곱셈의 경계 오류, 실제 키 불일치, 큰 FFT 비용, 입력 의존
   실행시간이 함께 있다. 통합 ref에 반영하지 않는다.
3. 다음 수정 시 위 5개 seed와 작은 곱셈 반례를 고정 회귀시험에 포함한다.
   먼저 실제 5개 seed의 첫 차이를 추적하고, 필요한 정밀도/절삭 의미와 적용 범위를
   정해야 한다. 단순 floor 추가나 seed 특례로 통과시키지 않는다.
4. 지수 의존 분기는 실제 출력 ASM에서 제거했는지 확인해야 한다. 여기서는
   crypto 수정 없이 실패를 확인한 것이며, 제거·재설계까지 완료한 것은 아니다.

기존 ITCM ECC 문제로 분류하지 않는다. 완료한 재측정에는 fault가 없었다.
