# 1.7배 목표: 추가 문헌과 실제 solver 대조

2026-09-28. A16/B18 이후의 **분석 기록**이다. 암호 소스, 반복 정책,
KAT 기준, 빌드 환경은 변경하지 않았다. 새 보드 성능 결과도 아니다.

## 새로 확인한 일차 문헌

[Teixeira, Gazzoni Filho, López Hernández, Improving FALCON’s Key Generation
on ARMv8-A Platforms](https://sol.sbc.org.br/index.php/sbseg/article/download/27234/27050)
PDF **1–6쪽 전체**를 읽었다. 내려받은 PDF SHA-256:
`397dbec0ed7abfa1c8d9b81f8022adfb4e13bd7f32cef0ac8c4cc039665184b8`.
기존 `extract_papers.swift`로 페이지별 텍스트를 추출했다.

- 깊은 재귀의 큰 계수에 대해 임의 정밀도 연산으로 Babai 축소의 반복을
  줄이는 방향을 FLINT로 시험했다. Apple M1/Cortex-A72의 **축소 단계**
  실험이며, 얕은 단계에는 임의 정밀도 비용이 불리하다 (§4–5).
- 31/63-bit RNS 소수를 섞어 스칼라/SIMD를 활용하는 별도 제안도 있다.
  이 부분은 구현·실측이 남은 제안으로 구분한다 (§5, 마지막 쪽).
- 라이브러리의 상수시간 보장은 없으며, 이를 요구하면 성능이 달라질 수
  있다고 명시한다. 우리 M55 성능·기존 KAT 일치의 근거는 아니다.

[Bros, Celi, Ciadoux, Perlner, Black-box validation of Falcon key generation
under numerical instability](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=961306)
는 초록과 수치 불안정·키 차이·검증 관련 절을 대조했다. 이번에 재확인한
핵심은 **§4.2.2, 인쇄 12쪽**이다. 전체 23쪽을 이번에 모두 읽었다고
주장하지 않는다.

- 축소 반복 한도와 반올림이 키 후보의 거부 또는 최종 키 차이를 만들 수
  있다고 설명한다. 대체 검증 방법을 제안하지만 부채널 검증은 별개다.
- 여기서 요구한 **원본 KAT 바이트 일치**는 그대로 유지한다. 논문을
  근거로 불일치를 통과 처리하지 않는다.

## 우리 코드에서 직접 확인한 차이

아래 판단은 논문의 M55 결과가 아니라 현재
`A_tw_bridge/kgen_ntru.c`의 스칼라 `solve_NTRU_intermediate()` 분석이다.

| 항목 | 현재 코드 | 적용 시 필요한 검토 |
| --- | --- | --- |
| 축소식 | 중간 단계는 `k ≈ round(F/f)`로 F를 줄이며 끝에서 마무리 | 논문의 F와 G를 함께 사용하는 식과 동일한 코드가 아님 |
| 입력 정밀도 | 공개된 자리 창과 비밀 scale_x로 Q32 근사 입력 생성 | double만 사용한다고 큰 정수의 모든 유효 비트를 보존하지 못함 |
| 변하지 않는 피연산자 | f의 FFT와 역수는 반복 전에 한 번 계산 | 이미 재사용하므로 반복마다 이 역수를 제거하는 새 이득은 없음 |
| 반복 정책 | 최상위 512는 reduce_bits=9, 1024는 8 | 숫자만 늘리면 원래 k·실패 지점·KAT 일치가 유지된다는 근거가 없음 |
| 정수 갱신 | 매 반복 `poly_sub_*()`로 전체 폭 F를 갱신 | 여러 반복을 합치는 것은 FFT 명령 스케줄 변경과 다른 작업 |
| 종료·거부 | 공개 scale/길이 감소와 잘라낸 자리의 부호 확장 검사 | 새 방식의 성공만 확인하지 말고 원래 거부 후보도 대조해야 함 |

따라서 임의 정밀도 접근을 **기존 FP64/2×FP32 FFT의 교체품**처럼
바로 넣을 수 없다. 더 높은 정밀도, k 저장 폭, 정수 갱신, 실패 조건,
상수시간 접근과 작업공간을 묶어서 설계해야 한다. 현재의 2×FP32 Q32
호환 표현을 유지하는 실험과는 다른 범위다.

## 실측 로그가 보여 주는 범위

[재현 가능한 재집계](../validation/scope_feasibility.md)는 원본·ntt_opt·A16의
소스/ELF/로그 해시를 확인한다. 218개 계측 항목에서 호출·성공 횟수가
모두 일치했다. 부모 구간과 자식 구간은 중복해서 더하지 않았다.

- 실제 비계측 전체 키생성: A16은 M55_ref 대비 **1.1666×/1.1151×**.
- 기존 NTT 개선을 포함하더라도, A16의 대상 FFT 구간을 0 cycles로
  놓고 다른 계측 시간을 유지한 가정은 **1.2621×/1.1668×**.
- 범위 밖 `I_update`까지 0으로 놓은 더 과감한 가정도 **1.7793×/1.6234×**.
  1024에서는 여전히 1.7배에 미달한다.

이 수치는 **조건부 회계 계산**이다. 실제 구현 성능, 계측 없는 엄밀한
하한, 모든 새로운 알고리즘의 불가능성 증명이 아니다. 특히 새 알고리즘이
재시도·복원·CRT·부모 제어까지 바꾸면 고정된 나머지 시간이라는 가정이
성립하지 않는다. 그러나 같은 작업량을 유지하며 대상 FFT의 명령만
단축하는 현재 방향에 1.7배를 약속할 근거는 없다.

후보 직교노름 검사의 invnorm도 이 NTRU-only 범위에는 들어 있지 않다.
그 함수를 교체한 성과를 이번 NTRU FFT 개선으로 합산하지 않는다.

## 다음 의사결정

현재 범위에서 검증된 최선은 A16, 코드 크기를 아끼는 대안은 A15다.
더 작은 명령·배치 개선은 가능할 수 있지만 위 전체 목표의 해결책이라고
보지는 않는다. 모든 가능한 최적화를 소진했다는 주장도 하지 않는다.

1. 범위를 유지하면 A16의 검증된 개선과 목표 미달을 그대로 보고한다.
2. 1.7배 목표를 계속 추구하려면 Babai 반복/정수 갱신 또는 다른 큰 구간까지
   연구할지 범위를 먼저 결정해야 한다. **Babai만 변경하면 충분하다는
   보장도 없다.**
3. 승인된다면 새 독립 후보에서 동일 입력의 원래 k·실패 지점을 먼저
   대조하고, 원본 KAT·방정식·서명·시간·메모리 검증을 통과한 후보만
   전체 성능 비교에 올린다. 임의의 반복 감소나 비밀값 기반 빠른 우회는
   지금 적용하지 않았다.

앞서 물은 반복 정책 확장에는 아직 응답이 없으므로 이번에는 문헌과
프로파일 분석까지만 했다. 기존 A16/B18의 생산 소스와 기준 폴더는 그대로다.
