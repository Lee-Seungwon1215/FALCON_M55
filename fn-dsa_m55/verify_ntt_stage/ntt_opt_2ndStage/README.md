# FN-DSA M55 NTT 2단계 레이어 병합 실험

`ref`는 2단계 시작 당시 `fn-dsa_m55/ntt_opt`의 1단계 MVE 구현을 고정한
스냅샷이다. 여섯 후보는 각 폴더의 `mq_cm55.s`만 다르고, 나머지 FN-DSA
소스는 `ref`와 같다.

최종 선택은 FN-DSA-512의 `512_3layer_232`와 FN-DSA-1024의
`1024_2layer`이다. 두 경로는 빌드 스위치 없이 `../ntt_opt/mq_cm55.s`에 직접
병합했으며, 병합된 파일의 pilot과 100회 full 측정도 통과했다.

## 후보

| 폴더 | Forward NTT | Inverse NTT | 적용 크기 |
|---|---|---|---|
| `512_2layer` | `2+2+2+1`, 마지막 2 | 반대 순서의 GS 구조 | FN-DSA-512만 |
| `512_3layer_223` | `2+2+3`, 마지막 2 | 마지막 2 → `3+2+2` | FN-DSA-512만 |
| `512_3layer_232` | `2+3+2`, 마지막 2 | 마지막 2 → `2+3+2` | FN-DSA-512만 |
| `512_3layer_322` | `3+2+2`, 마지막 2 | 마지막 2 → `2+2+3` | FN-DSA-512만 |
| `1024_2layer` | `2+2+2+2`, 마지막 2 | 반대 순서의 GS 구조 | FN-DSA-1024만 |
| `1024_3layer` | `2+3+3`, 마지막 2 | 반대 순서의 GS 구조 | FN-DSA-1024만 |

`마지막 2`는 1단계에서 이미 구현한 마지막 두 레이어의 `VLD4/VST4` MVE
경계를 그대로 사용한다는 뜻이다. 모든 후보는 q=12289 Montgomery 표현,
GM/iGM 순서, canonical 메모리 배열을 유지한다. 분기와 주소는 공개 `logn`과
고정 반복 횟수에만 의존한다.

## 빌드 및 보드 조건

- 보드: NUCLEO-N657X0-Q, Cortex-M55 r1p1
- CPU/SYSCLK/HCLK: 800/400/200 MHz
- 코드: ITCM 256 KiB, 데이터·상수·스택: DTCM 256 KiB
- I-cache/D-cache: 실행 중 OFF
- TCM ECC 검사: 실행 전후 ON (`TCM_MSCR=0x1300a`)
- GNU Arm 15.2.1, Zephyr 4.4.1, `-O3`
- `mlkem-native` Nucleo 설정과 기존 로더/측정 harness 유지
- 각 degree·operation: 10개 입력 batch
- batch마다 10회 warm-up 뒤 10회를 한 block으로 측정
- 아래 값: 10개 block의 upper median을 10으로 나눈 cycle/call

## 코드 크기와 판단

| 구현 | `mq_cm55.o` `.text` | `ref` 대비 증가 | SHA-256 (`mq_cm55.s`) |
|---|---:|---:|---|
| `ref` | 2,856 B | - | `7a2a83bc070afc85bad8211f632999ed1b9557f60118fb9476c43d98ba0d01fd` |
| `512_2layer` | 4,208 B | +1,352 B | `5a0700a19c349abb1b6433a408b4d515417c032a3e92cb157dfa6ee8d2b5dc7d` |
| `512_3layer_223` | 7,796 B | +4,940 B | `a82665f29a740f6fe74c54ab57ba4bf8f404883c782e77e09a93e7a5639de10d` |
| `512_3layer_232` | 9,056 B | +6,200 B | `441d123cbe5bcdb3d3064336d74ad0861fa974d2dcbd361704807b5de9ae10a0` |
| `512_3layer_322` | 9,044 B | +6,188 B | `3832cc17fffd5f6af8e89a070884f5b16a372f12e65e31d896c70ae82fd1ac07` |
| `1024_2layer` | 4,308 B | +1,452 B | `095b8e250f20e15d1723a84018c710c21b5ecf8810951a2dcfd2821ea6426528` |
| `1024_3layer` | 10,052 B | +7,196 B | `6f5aa2558e0141472a7aac29082fcd758fba00af07923095dd02a0e9b43eb10c` |

- 512에서는 `232`와 `322`가 전체 연산 기준으로 사실상 같은 성능이다. keygen/sign
  차이는 각각 300/120 cycles에 불과하고, verify는 `322`가 10 cycles 빠르다.
- `223`은 `232`보다 `.text`가 1,260 B 작지만, 네 lane만 유효한 늦은 CT3/GS3의
  명령·load/store 비용 때문에 기준 `ref`보다 sign/verify가 느려졌다.
- 이번 통합은 end-to-end 결과와 구현 안정성을 기준으로 `232`를 선택했다.
  향후 논문에서 `232` 레이어 배치 자체의 우위를 주장하려면 별도 NTT/iNTT
  microbenchmark가 필요하다.
- 1024에서는 `3-layer`의 추가 load/store와 4-lane 꼬리 처리 비용이 이득보다 커서
  `2-layer`가 cycle과 크기 모두 우세하다.
- keygen의 0.1% 미만 차이는 후보 판단 근거로 약하다. 입력별 NTRU 재시도 때문에
  분산이 크다. sign/verify 및 별도 NTT/iNTT microbenchmark를 우선 판단 기준으로 삼는다.

## 검증 중 수정한 오류

초기 `1024_2layer`에는 `logn != 10` 일반 forward 경로가 전용 `F2_setup`으로
fall-through하는 분기 누락이 있었다. 실제 보드에서 FN-DSA-512 keygen 중 fault로
재현했으며, 일반 경로를 기존 `L4`로 보내는 고정 분기를 추가했다. 임시로 시험한
ITCM padding은 제거했다. 위 결과와 해시는 이 수정 이후의 최종 소스 기준이다.
