# B / C 정적 스택 사용 감사

2026-09-27. **보드 watermark 측정이 아닌, 현재 컴파일러의 정적 프레임 + 호출 경로 분석**이다.
후보 소스·실행 ELF·기존 빌드 산출물은 변경하지 않았다.

## 결론

현재 B와 C의 키생성 호출 경로는 설정된 **64 KiB main stack 안에 충분히 들어가는 정적 구조**다.

| 경로 | 보수적 암호 함수 체인 상한 | 65,536 B 대비 여유 |
| --- | ---: | ---: |
| 측정 프로그램처럼 유효한 외부 `tmp`를 전달 | **17,656 B** | 47,880 B |
| `tmp == NULL`인 일반 API의 1024 내부 임시배열 경로 | **40,200 B** | 25,336 B |

이 수치는 호출자·OS·예외 진입 프레임을 포함한 보드 최대 사용량이 아니다. 알려진 암호 호출 경로의
정적 보수 경계다. 두 DS 배열을 가진 intermediate와 depth0는 **서로 중첩 호출되지 않는다**.
같은 크기의 배열 두 개를 각각 별도 함수가 가진다고 해서 32 KiB로 합산하지 않는다.

## 방법과 컴파일러

- Arm GNU Toolchain 15.2.Rel1, GCC **15.2.1 20251203**.
- 각 후보 `validation/build/kat/compile_commands.json`에서 실제 19개 C translation unit의 명령을 가져왔다.
- 기존 `-O3 -mcpu=cortex-m55 -mfpu=fpv5-d16 -ffp-contract=off -fno-fast-math`와
  ASM/MVE 정의를 유지하고, **진단용으로 `-fstack-usage`만 추가**했다.
- `-MD/-MMD/-MP/-MF/-MT/-MQ` 의존성 출력 옵션과 기존 `-o`를 제거했다.
  따라서 원래 build의 object/dependency/ELF를 덮어쓰지 않았다.
- 출력은 `/private/tmp/fndsa-bc-stack-audit.ambmA5/B_final/`,
  `/private/tmp/fndsa-bc-stack-audit.ambmA5/C_final/`의 object와 `.su`뿐이다.
  임시 디렉터리이므로 영구 재현 자료는 아래 명령 조건·소스 hash와 본 표다.
- 두 후보 각각 컴파일 전후 모든 루트 C/H/S SHA-256을 비교했고 **변경 없음**을 확인했다.
- 관련 C 프레임은 모두 GCC `static` 분류였다. ASM의 저장 레지스터와 `sub sp`는 소스와 ELF에서 별도 확인했다.
- 실제 ELF의 직접 호출/꼬리 호출을 확인하여, 크기별 wrapper 및 intermediate/depth0의
  **배타적인 경로**를 구분했다. 단순히 모든 함수 프레임을 더하지 않았다.

## 최종 소스에서 얻은 프레임

컴파일 시각: B 2026-09-27T06:06:15.751081+00:00, C 2026-09-27T06:06:16.571168+00:00.

| 함수·프레임 | B bytes | C bytes |
| --- | ---: | ---: |
| `fndsa_keygen_seeded_temp` | 56 | 56 |
| `keygen_inner` | 256 | 256 |
| `fndsa_solve_NTRU` | 56 | 56 |
| `solve_NTRU_intermediate` | 16,568 | 16,568 |
| `solve_NTRU_depth0` | 16,568 | 16,568 |
| DS forward 제어 | 344 | 344 |
| DS inverse 제어 | 376 | 376 |
| B Q32 export / C direct-to-k | 232 | 48 |
| B Q32 import / C big integer import | 72 | 400 |
| `poly_sub_scaled` | 616 | 616 |
| `zint_add_scaled_mul_small` | 56 | 56 |
| no-temp `keygen_1024.constprop` | 22,800 | 22,800 |

각 NTRU 프레임의 대부분은 DS workspace **8,192 B × 2**다.
C의 `fndsa_ds_ifft` wrapper 자체는 0 B이며, 꼬리 호출되는 `ds_ifft_run`이 376 B다.

ASM 함수 자체 프레임:

- 일반 DS butterfly helper: 344 B = 정수 레지스터 저장 24 + scratch 320.
- 활성 span forward/inverse: 128 / 160 B.
- 활성 packed tail forward/inverse: 136 / 168 B.
- 기존 RNS NTT/iNTT 정상 경로: 112 B.
- 기존 SHA3 block: 184 B.

위 상한은 활성 경로보다 큰 일반 helper까지 포함해 DS 자식 최대를
`376 + 344 = 720 B`로 보수적으로 잡았다.
큰 변환의 실제 packed/span 경로는 이보다 작다.

```text
외부 tmp 제공:
56 + 256 + 56 + 16,568 + 720 = 17,656 B

tmp == NULL, n=1024:
56 + 22,800 + 56 + 16,568 + 720 = 40,200 B
```

22,800 B wrapper에는 keygen_inner가 인라인되어 있으므로 256 B를 다시 더하지 않는다.
정수 갱신 자식 체인 `616 + 56 = 672 B`는 보수 DS 자식 경계 720 B보다 작다.

## 소스 개정 구분

최초 진단(약 06:00 UTC)에서는 B depth0가 **16,576 B**, export가 136 B였다.
그때 전달한 보수 경계 **17,664 / 40,208 B**는 **출력 경계 보정 전 소스**에 해당한다.

그 후 B의 TwoSum 경계 보정·유효성 검사·0 분모 실패 반환이 추가되었다.
06:06 UTC 재컴파일의 최종 경계는 **17,656 / 40,200 B**이며 export 프레임은 232 B다.
작은 프레임 감소는 컴파일러 배치 변화이지 수치 보정을 제거했다는 뜻이 아니다.

## 아직 검증하지 않은 부분

- 실제 보드의 main stack watermark / guard canary / 최악 입력 high-water.
- 모든 호출자와 인터럽트 중첩을 포함한 형식적 최대 스택 증명.
- 모든 키생성·서명 API의 전체 호출 경로. 이번 수치는 **키생성** 대상이다.
- static bound가 메모리 안전성·수치 정확성·상수시간을 대신하지 않는다.

확인한 보드 설정은 `CONFIG_MAIN_STACK_SIZE=65536`, `CONFIG_ISR_STACK_SIZE=2048`이다.
ISR stack과 main stack은 구분하되, 예외 진입 시 main stack에 저장되는 프레임을 0으로
가정해서는 안 된다. 현 정적 암호 체인은 그 여유를 남긴다.
