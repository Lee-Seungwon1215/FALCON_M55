# Native FP64 KAT 불일치: 캐리·변환 재검사

2026-09-23. 대상은 `1st_native_fp64` 루트의 `double re, im` 구현이다.
후속 `fp64_two_prod`의 `double hi, lo` 정확 재현 구현과 구분한다.

## 결론

이번에 재현한 불일치에서 **캐리 전달 누락의 증거는 발견하지 못했다.**
원본 Q32.32의 연산별 절삭·범위 wrap과 native double의 반올림 규칙 차이를
확인했다. 원본이 버리는 하위 비트를 FP64가 유지하면, 역수 준비에서 작은
분모의 상대 차이가 커지고 최종 정수 k가 달라질 수 있다.

암호 구현 소스는 수정하지 않았다. 진단 소스와 새 결과만 추가했다.
이번 실행은 **Mac 호스트 검사**이며 M55 보드 재실행, 새로운 전체 KAT300,
서명 검증 또는 상수시간 인증을 수행했다는 뜻이 아니다.

raw word 추가 시험은 실제 `poly_big_to_fp64()`를 호출했다. 기대값은
정확한 유리수 `signed(raw)/2^32`를 binary64로 반올림한 값이다.
10,050개 중 9,937개는 정확한 유리수와 같지 않지만 **올바르게 반올림된 값**이다.
임의의 Q32.32 64-bit 값을 double 하나로 모두 정확히 표현할 수 있다는 뜻은 아니다.
이번 26개 최초 불일치의 `f`, `F` 입력에는 이러한 변환 손실이 없었다.

## 26개 불일치 입력의 첫 다른 k 재현

- 기존 불일치 목록 26개를 새 실행 파일로 모두 재현했다.
- 각 첫 불일치에서 원본 raw 입력과 double 입력 간 변환 손실: **0**.
- 같은 raw 입력·같은 root 상수를 사용하는 Decimal 80자리 계산과 native FP64의
  반올림된 k 차이: **26개 사례 모두 0**.
- 역수 준비 결과를 원본 값으로 교체하면 해당 첫 불일치 지점의 k 차이:
  **26개 사례 모두 0**. 여기서 역수 준비는 FFT·제곱합·나눗셈 전체를 포함한다.

이는 첫 관찰 지점에 대한 결과이지, 그 교체만으로 모든 후속 계산과 전체 KAT가
같아진다는 뜻은 아니다. 고정밀 oracle도 유한 정밀도이며 전체 수학적 증명이 아니다.

## 대표 사례: 512/test43, depth=7, logn=2, round=388

입력 변환부터 잘못됐는지 먼저 확인했으나 raw 입력이 모두 정확히 전달됐다.
첫 FFT butterfly의 두 구현에 공통인 곱셈에서:

| 연산 | fixed | native double |
|---|---:|---:|
| `ac` | -2525.5894411278423 | -2525.5894411278423 |
| `bd` | -2658.572088548215 | -2658.5720885481737 |

`bd`의 원본 곱셈은 정확한 정수 곱을 32-bit 우측 이동하며 나머지
767,225,908을 버린다. 컴파일된 fixed 결과를 임의 정밀도 정수 곱과 대조해
일치했다. 캐리를 계산하다 놓친 것이 아니라 Q32.32 절삭 규칙이다.
`ac`도 수학적으로 하위 비트를 버리지만 이 입력에서는 double 반올림 결과가
fixed 값을 double로 옮긴 값과 우연히 같다. 따라서 '첫 절삭'과 '첫 관찰되는
수치 차이'를 동일시하지 않았다.

이후 역수 준비의 분모 `re*re + im*im`에서 차이가 증폭된다. 원본 FFT 출력의
두 작은 성분 raw word는 -103775, -352340이다. 정확한 제곱을 Q32.32 raw 단위로
나타내면 각각 약 2.5074115547, 28.9044053294이다.

```text
원본: 각각 절삭한 뒤 더함 → 2 + 28 = 30
각각 절삭하지 않은 합     → 약 31.4118168841
실제 native 경로 분모    → 약 31.4118377768 (FFT 출력에도 이미 작은 차이가 있음)
```

두 제곱에서 버리는 나머지를 합치면 2^32보다 크지만, 원본은 각 제곱 단계에서
이미 이를 버린다. 나중에 그 잔여값으로 자리올림을 복원하는 것이 원본 규칙은 아니다.
허수부의 캐리를 실수부에 전달할 문제가 아니라 **두 제곱 결과의 양자화 시점** 문제다.

| 지점 | 원본 fixed | native FP64 |
|---|---:|---:|
| 작은 분모 | 6.984919309616089e-9 | 7.313638407916152e-9 |
| index 2, 정수 k 반올림 직전 | 24.557566086994484 | 23.44621494072141 |
| 반올림한 k | 25 | 23 |

분모 상대 차이는 약 4.7061%이다. 최종 반올림 이전에 값이 이미 달라졌다.
고정밀 계산의 해당 k도 23이다. 이 사례는 단순히 마지막 정수변환에 캐리 하나를
더하는 방식으로 해결할 문제가 아님을 보여준다. 원본 구현의 암호학적 오류를
판정한 것이 아니라, 서로 다른 산술 규칙을 사용하는 사실을 확인한 것이다.

## 역수 준비를 원본으로 바꿔도 남는 후속 차이

두 사례를 다시 실행하고 FFT·점별곱·iFFT 각각의 경계에서 원본 C 출력과 독립
정수 모델의 raw word가 일치하는지 확인했다.

- 512/test58, round=769: 점별 곱에서 64-bit 범위 wrap 발생, 총 5회. k 63개 차이.
- 1024/test65, round=1258: wrap은 없지만 단계별 절삭·연산 순서 등의 차이로 k 1개 차이.

그러므로 다음 검토 대상은 캐리 반환 코드 추가가 아니라, 원본의 **역수 준비·연산별
절삭·범위 처리 중 어떤 규칙을 보존해야 하는가**이다. 기존 정확 재현보다 가벼운
방법이 가능한지는 별도 연구가 필요하며, 이번 진단에서 해결 구현을 채택하지 않았다.
