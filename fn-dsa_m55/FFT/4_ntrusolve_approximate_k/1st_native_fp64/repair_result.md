# KAT·시간 차이·반복 구간 속도 후속 조사

2026-09-18. **부분 수정 완료. 세 조건을 모두 충족한 채택본은 아니다.**

| 문제 | 조치·결과 | 남은 사항 |
|---|---|---|
| 기존 KAT 불일치 | 26건 모두 첫 k 차이를 추적. 모두 FP64 k가 80자리 oracle과 일치 | 현재도 26/300 불일치. 기존 산술과 출력 호환성을 유지할 설계 선택 필요 |
| FP64 나눗셈 시간 차이 | 항상 정상 mantissa만 VDIV에 입력하도록 수정. 시험한 20종의 256회 호출 시간이 모두 36,360 cycles | 이 primitive의 발견된 문제를 처리한 것. 전체 키생성의 상수시간·전력/EM 안전성을 증명한 것은 아님 |
| 반복 계산 속도 저하 | C 복소 곱셈을 3곱/5합에서 4곱/2합으로 수정 | 초기 FP64보다 5.57~8.40% 개선했지만 고정소수점보다 아직 1.64~1.82배 느림 |

원본 `../ref`, `fn-dsa_m55/ntt_opt`, 모든 assembly 파일 및 2nd~5th 폴더는 수정하지 않았다.
현재 `1st_native_fp64`의 산술 코드는 **native FP64 수정 후보**이며 채택본이 아니다.
KAT를 새 값으로 덮거나, 특정 seed를 예외 처리하거나, 몰래 고정소수점으로 fallback하지 않았다.

## 1. KAT: 구현 실수와 산술 정의의 차이를 분리

`validation/revision/diagnose.py`는 원본 고정소수점 NTRU의 정수 상태를 그대로 진행하면서,
같은 입력으로 FP64를 별도 계산한다. 각 불일치 seed에서 최초로 정수 k가 달라지는 지점을
저장하여, 이미 달라진 정수 상태를 비교하는 오류를 피했다.

512의 8건, 1024의 18건 **전부** 다음을 확인했다.

- 첫 차이에서 FP64의 반올림 k는 Decimal 80자리 계산과 일치했다.
- 역수 준비 결과만 원래 고정소수점 결과로 대체하면 그 **첫 번째** 차이는 사라졌다.
- 이는 전체 후속 계산이나 최종 KAT까지 같아진다는 뜻은 아니다.

대표 `512/test43`의 작은 분모는 다음과 같았다.

| 값 | 고정소수점 | FP64 |
|---|---:|---:|
| FFT f의 작은 성분에서 `re²+im²` | 6.984919309616089e-9 | 7.313638407916152e-9 |
| 한 출력 계수의 근삿값 | 24.55756608699 | 23.44621494072 |
| k | 25 | 23 |

Q32.32에서는 각 제곱의 하위 비트를 버린다. 작은 분모에서는 이 양자화 차이가
역수에서 확대된다. double이 이 양자화를 하지 않는 것은 단순 코딩 버그가 아니라
산술 정의의 차이다. root를 동일하게 유지해도 각 연산의 반올림까지 같아지지는 않는다.

### 일부만 원래 산술로 되돌리는 진단 실험

본 소스에 채택하지 않고 `validation/revision/compatibility/`에서만 시험했다.

| 진단 구성 | 기존 keygen KAT 불일치 |
|---|---:|
| 준비·반복 모두 native FP64 | 26/300 |
| 준비만 원래 고정소수점, 반복은 FP64 | 2/300 |

남은 두 경우도 추적했다.

- `1024/test65`: 반복 FFT 산술 차이로 한 계수가 `-1442.5005167` 대 `-1442.4982897`이 되어 정수 k가 달라졌다.
- `512/test58`: 작은 오차만의 문제가 아니었다. 반복 경로의 Q32.32 범위/wrap 효과로 출력 차이에 `2^28` 같은 큰 값이 나타났다. 전체 FP64는 원래의 64-bit wrap 산술과 같지 않다.

이 두 진단 레코드는 `compatibility/*first-repeat-difference.json`에 보존했다.
후자의 모든 primitive 중 어느 연산에서 최초 wrap이 일어나는지까지 개별 역추적한 것은 아니다.
혼합 진단은 전체 signature KAT는 통과했지만 keygen KAT 2건은 여전히 실패했다.
따라서 이를 KAT 해결본으로 채택하지 않았다.

**결론:** 현재의 더 정밀한 FP64 계산을 유지하면서 기존 고정소수점 답을 그대로 요구하면
이미 확인한 입력에서 두 요구가 충돌한다. 기존 KAT를 유지하려면 필요한 Q32.32
양자화·범위 의미를 보존하는 호환 구현/혼합 구현을 설계해야 한다.
사용자 승인 없이 KAT 요구를 해제하거나 최적화 목표를 그 방향으로 바꾸지는 않았다.

데이터: [26건 요약](validation/revision/diagnosis/summary.json),
[진단 소스 manifest](validation/revision/diagnosis/manifest.json),
[혼합 진단 KAT 로그](validation/revision/compatibility/kat.log).

## 2. 나눗셈: 수정과 검증 범위

`kgen_inner.h`에 `fp64_div_normal()`을 추가하고 역수 준비의 두 나눗셈에서 사용했다.

1. 입력의 부호·지수·가수를 정수 비트 연산으로 분리한다.
2. 실제 VDIV에는 항상 양수 `[1,2)`의 정상 가수만 넣는다.
3. 정상 결과는 지수·부호 비트를 복원한다. 정상 범위에서 2의 거듭제곱 재조정은 정확하다.
4. `±0 / normal`은 부호 있는 0으로 복원한다.
5. 지원하지 않는 도메인은 quiet NaN을 반환하여 기존 checked k 변환이 후보를 거부하게 한다.

지원 도메인은 **정상 입력과 정상 출력, 또는 0/정상 입력**이다.
이 함수는 모든 IEEE-754 값을 지원하는 일반 나눗셈 API가 아니다.
subnormal·Inf·NaN·0 분모·범위 밖 결과를 유효한 수치 결과로 가장하지 않는다.
지원 도메인 밖 후보를 거부할 수 있다는 의미 역시 후속 보안/분포 분석에서 검토해야 한다.

호스트의 무작위 정상 입력 200,000쌍 중 결과까지 정상인 149,882쌍에서
원래 double 나눗셈과 **bit-for-bit 일치**했다. 나머지 범위 밖 결과 50,118쌍 및
별도 경계/특수값 20개는 선언한 처리와 일치했다.

최종 M55의 같은 함수 주소에서, 클래스별 warm-up 1 + 측정 20 trial,
trial당 256회 호출로 비교했다.

| 경로 | 입력 | min~max cycles / 256회 |
|---|---|---:|
| 원래 `a/b` | 0/1 | 3,846~3,846 |
| 원래 `a/b` | 1/1 등 비영 입력 | 10,502~10,502 |
| 수정 함수 | 정상 12종 + -0/0분모/Inf/NaN/subnormal/범위 밖 등 총 20종 | **전부 36,360~36,360** |

루프·호출·load/store를 포함한 값이며 단일 VDIV의 latency가 아니다.
수정 함수는 추가 정수 처리 비용이 있어 원래 정상 입력 나눗셈보다 느리다.
ELF에서 VDIV 전에 가수가 정상 범위로 구성되는 것, 함수 내부의 데이터 의존 분기 없이
mask/predication으로 복원하는 것을 확인했다. stack spill 주소와 접근 횟수도 고정이다.

Arm 가이드의 Table 3-15는 정상 double 나눗셈과 0/Inf/NaN/invalid 입력의
latency가 다름을 명시한다. 관측된 차이와 일치한다.
[Arm Cortex-M55 r1p1 Software Optimization Guide, pp.32–34](https://documentation-service.arm.com/static/63ac5ce1396e6135830ba9fe)

**발견했던 나눗셈 special-input 시간차는 수정·재시험했다.** 다만 finite sample 측정과
한 함수의 정적 검토를 전체 FN-DSA의 상수시간 증명으로 확대 해석하지 않는다.
키생성의 후보 거부·재시도 시간은 원래부터 일정한 횟수로 고정된 것이 아니며,
모든 비밀 입력에서 중간값이 허용 범위에 있다는 형식 증명과 전력/EM 평가는 하지 않았다.

## 3. 느린 이유와 C 수정 효과

soft-double library를 잘못 호출해서 느린 것은 아니었다. 최종 ELF에 native FP64 명령이
있고 `__aeabi_d*` 산술 helper는 없다. Arm Table 3-15의 FP64 덧셈/곱셈 latency는
각각 15/21 cycles로, 하드웨어 지원이 곧 최적화된 정수 경로보다 빠르다는 뜻은 아니다.
[Arm 공식 가이드](https://documentation-service.arm.com/static/63ac5ce1396e6135830ba9fe)

C 복소 곱셈을 다음처럼 바꿨다. fused-FMA나 assembly는 도입하지 않았다.

- 초기: `ac, bd, (a+b)(c+d)` → 곱셈 3회, 덧셈/뺄셈 5회.
- 수정: `ac, bd, ad, bc` → 곱셈 4회, 덧셈/뺄셈 2회.

이 변경은 원래 **2nd complex multiplication의 실험 축과 겹친다**.
이번에는 요청한 속도 저하 대응으로 후보를 시험했으며, 2nd 폴더 전체를 구현하거나
초기 3곱셈 기준점을 없앤 것이 아니다. 초기 소스·결과는 아래 archive에 있다.

같은 실제 입력, logn별 2개, 각 100회 평균의 반복 구간(FFT+곱셈+iFFT+반올림)이다.

| 내부 logn | 초기 FP64 cycles | 수정 FP64 cycles | 초기 FP64 대비 감소 | 수정 FP64 / 고정소수점 시간 |
|---:|---:|---:|---:|---:|
| 1 | 331 | 308 | 6.95% | 1.822배 |
| 2 | 1,226 | 1,123 | 8.40% | 1.639배 |
| 3 | 3,339 | 3,073 | 7.97% | 1.673배 |
| 4 | 8,294 | 7,686 | 7.33% | 1.688배 |
| 5 | 20,217 | 18,844 | 6.79% | 1.734배 |
| 6 | 47,780 | 44,738 | 6.37% | 1.766배 |
| 7 | 110,383 | 103,720 | 6.04% | 1.788배 |
| 8 | 250,586 | 236,110 | 5.78% | 1.804배 |
| 9 | 561,029 | 529,780 | 5.57% | 1.816배 |

**고정소수점보다 빨라진 것은 아니다.** 수정 후 준비 구간은 고정소수점보다
3.75~8.27배 빠르지만, 원래 native 준비보다는 나눗셈 보정 비용이 추가됐다.
함수별 실행 주소를 서로 동일하게 고정한 실험은 아니므로 작은 차이에 대한 배치 영향은
배제하지 않는다. 19개 고정 입력의 각 backend 결과는 호스트 기대값과 일치했다.

## 4. 전체 키생성 재측정

기존과 동일한 M55 800 MHz, cache OFF, ITCM code/DTCM data·stack,
GCC 15.2.1, -O3, fpv5-d16, contraction/fast-math OFF,
크기별 100개 seed, DWT cycle 측정이다. 각 키의 정상 서명검증과 변조 거부도 검사했다.

| 키 크기 | 고정소수점 평균 | 초기 FP64 평균 | 수정 FP64 평균 | 초기 FP64 대비 감소 |
|---:|---:|---:|---:|---:|
| 512 | 57,007,002.15 | 56,136,451.98 | 55,764,784.24 | 0.6621% |
| 1024 | 243,375,295.54 | 223,032,366.38 | 222,043,026.20 | 0.4436% |

단위: cycles/call. 초기 FP64와 수정 FP64의 200개 키·서명 digest는 전부 같았다.
이 두 FP64 실행 사이의 성능 비교에서는 표본의 출력 키 변화가 없었다.
그러나 **고정소수점과는 여전히 KAT/후보 경로가 다르므로** 고정소수점 대비 전체 평균
감소를 순수한 산술 개선율이라고 부르지 않는다. 수정 FP64의 512 중앙값은
50,108,855로 고정소수점보다 4.07% 느리고, 1024 중앙값은 188,636,374다.

수정 후 ④ 준비/반복 구간의 전체 keygen 비중:

| 키 크기 | 준비 | 반복 |
|---:|---:|---:|
| 512 | 0.547% | 13.427% |
| 1024 | 0.298% | 9.286% |

최종 전체 펌웨어는 ITCM 102,596 B, DTCM 236,616 B(예약 stack 포함).
초기 FP64 대비 코드는 316 B 늘고 DTCM 사용량은 같다.

## 5. 검증 현황과 로그

- 입력 변환 112,530계수, rounding 10,044개, invalid conversion 8개, update bound 70개: PASS.
- FFT/iFFT 40개 및 실제 k 19개 레코드: 고정밀 비교 PASS. 실제 19개에서 최대 절대오차 약 1.408e-6, 반올림 k 모두 oracle과 일치. 전 입력의 오류 확률 증명은 아님.
- 기존 keygen KAT: **274/300**, 기존 전체 signature KAT **FAIL**. 기대값은 수정하지 않음.
- 키 관계·범위 검사, 정상 서명검증·변조 거부, 표적 UBSan/float-cast-overflow: PASS.
- 새 divider: 정상 결과 149,882개 bit 일치; 20개 M55 시간 클래스에서 같은 cycle.
- host/M55 perf/profile의 키·서명 digest: backend별 200/200 일치.
- 원본 baseline C/H/S hash 보존 확인, FP64 helper/FMA 여부 및 fault/ECC 확인.
- ASan/전체 프로그램 UBSan의 이전 제약은 그대로이며, 전체 안전성 PASS로 주장하지 않음.

## 다음 단계에 필요한 선택

기존 KAT를 반드시 유지하려면 고정소수점의 양자화·범위 의미를 보존하는 구현이 필요하다.
전체 native FP64를 유지한다면 기존 deterministic 출력과의 일치를 그대로 보장할 수 없고,
별도의 정확성·상호운용·보안 검증 기준을 사용자와 먼저 정해야 한다.
이 결정 전에는 현재 후보를 ref로 채택하거나 2nd~5th 폴더에 통합하지 않는다.
