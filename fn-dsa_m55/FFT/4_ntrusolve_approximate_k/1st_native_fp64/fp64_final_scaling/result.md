# iFFT 최종 정규화 FP64 후보 — 측정 결과

측정일: 2026-09-18. **실험·보드 측정 완료, 통합 ref 교체하지 않음.**

## 결론

- 기존 FP64 후보 대비 전체 키 생성 cycle: **512에서 1.0175%, 1024에서 0.7415% 감소**.
- 실제 키 생성의 ④ 근사 k 반복 구간: **7.5652%, 7.9741% 감소**.
- 큰 iFFT는 개선되지만 작은 크기(logn 1, 2)는 오히려 느리다.
- 전후 출력은 검사한 모든 사례에서 동일하다. **기존 원본 KAT 26/300 불일치는 그대로**이다. 이를 KAT PASS라고 해석하면 안 된다.
- 서명·검증·변조 거부 및 키 방정식·범위 검사는 통과했다.
- 제어된 iFFT 시간 시험에서는 20종 입력별 cycle 차이가 없었다. 전체 상수시간 증명이나 side-channel 안전성 인증은 아니다.
- 고정소수점보다 근사 k 반복 커널은 여전히 느리다. 이번 후보만으로 native FP64 전환을 최종 채택하지 않는다.

## 변경 범위와 근거

암호 코드에서 바뀐 파일은 `kgen_fxp.c` 하나, 함수는 `vect_iFFT_fp64()` 하나다.

기존 후보를 이 폴더에 독립적으로 복사했다. `1st_native_fp64`, 고정소수점 `../ref`, 통합 `ntt_opt`는 수정하지 않았다. 암호 소스 SHA256을 검사했으며 이 폴더와 기존 FP64의 차이는 `kgen_fxp.c`뿐이다.

| 구분 | 변경 전 | 변경 후 |
|---|---|---|
| 정규화 위치 | 각 butterfly의 실수 네 성분에 `×0.5` | 모든 레이어 뒤 각 실수 성분에 `×(2/n)` |
| 입력 변환·회전 상수·복소수 곱셈·나눗셈·반올림 | 기존 FP64 | 그대로 |
| reduction_bits 및 정수 해 갱신 | 기존 구현 | 그대로 |
| 대상 | `solve_NTRU_intermediate()`의 근사 k | 동일 |

근거: [Falcon PQClean iFFT](../../../../../falcon_ref/crypto_sign/falcon-512/clean/fft.c)의 마지막 정규화(335행 부근). 절반 복소수 저장 방식의 마지막 레이어를 생략하므로 최종 배율은 `1/n`이 아니라 `2/n`이다. 구현은 이 원리를 적용한 독립 C 코드이며 Falcon의 NTRU solver 전체를 이식한 것은 아니다.

`falcon_ref` clean의 `fpr`는 uint64로 저장한 IEEE binary64 에뮬레이션이다. FN-DSA keygen의 Q32.32 고정소수점과 같은 수치 형식이 아니다. 따라서 Falcon 방식을 참고했다는 이유만으로 원본 FN-DSA KAT와 같아지는 것은 아니다.

계약: `1 <= logn <= 10`, 중간 연산이 normal binary64 범위에 머무름(0 허용). 스케일을 뒤로 미루면 큰 중간값이 생긴다. 임의의 최대 finite/subnormal 입력에 대한 동등성은 주장하지 않는다. 실측 host 키 생성의 최대 iFFT 입력 절댓값은 약 `1.193e12`; 모든 관측 호출은 전후 bit-exact였다. 전체 입력 공간의 범위 증명을 완료한 것은 아니다.

## 측정 환경

- 보드: NUCLEO-N657X0-Q / STM32N657 / Cortex-M55.
- ST-LINK: `003C00223335510735383531`만 사용.
- 코어 800 MHz, 캐시 OFF, TCM_CONTROL `0x99`, ITCM/DTCM 재분할 각각 256 KiB.
- 코드 ITCM의 낮은 128 KiB 범위, 상수·데이터·스택 DTCM. 실제 코드 약 100 KiB.
- 기존 pinned `mlkem-native`/Zephyr 기반 보드 시작·메모리 설정 유지. 암호 구현은 각 후보 자체 소스.
- Arm GNU Toolchain 15.2.1, `-O3 -mfpu=fpv5-d16 -ffp-contract=off -fno-fast-math -fno-strict-aliasing`, 기존 M4/M55 ASM 및 MVE MP31 ON.
- DWT CYCCNT, 성능 구간 IRQ OFF, 키 크기별 `test0`…`test99` 100개 입력, 별도 warm-up.
- 프로파일용 펌웨어와 전체 성능 펌웨어를 분리. 원본 KAT 300개도 별도 펌웨어로 측정.
- 모든 채택 로그에서 CFSR/HFSR/AFSR=0, 시작·종료 TCM/ECC 설정 검사 통과.
- 호스트 검사는 정확성만 사용한다. 호스트 실행 시간을 M55 성능으로 보고하지 않는다.

## 전체 키 생성 — 같은 프로그램으로 새로 측정

평균 cycles, 100회. 감소율 = `(이전 FP64 − 이후 FP64) / 이전 FP64 × 100`.

| 키 크기 | 고정소수점 ref | 이전 FP64 | 이후 FP64 | 이전 FP64 대비 cycle 감소 |
|---|---:|---:|---:|---:|
| 512 | 57,007,002.12 | 55,764,784.24 | 55,197,356.31 | **1.0175%** |
| 1024 | 243,375,295.54 | 222,043,026.20 | 220,396,578.36 | **0.7415%** |

전후 FP64의 200개 키·서명 digest와 프로파일의 구간별 호출 횟수가 전부 같다. 따라서 이 비교에는 변경된 키 후보 채택/거부 경로에 따른 차이가 없다.

**고정소수점과 FP64는 결과 키와 후보 채택 경로가 일부 다르다.** 고정소수점 대비 평균은 각각 3.1744%, 9.4417% 낮지만, 이를 순수 FP64 산술 최적화 효과라고 주장할 수 없다.

## 실제 ④ 근사 k 반복 구간

구간은 정수→FP64 변환, FFT, FFT 곱셈, iFFT, k 반올림·범위 검사까지이다. FFT 한 함수만의 수치가 아니다. 아래는 100개 키 생성 동안의 누적 cycles이며 동일한 계측 오버헤드를 포함한다.

| 키 크기 | 호출 수(전후 동일) | 이전 FP64 | 이후 FP64 | cycle 감소 |
|---|---:|---:|---:|---:|
| 512 | 86,136 | 749,497,543 | 692,796,923 | **7.5652%** |
| 1024 | 218,396 | 2,063,276,450 | 1,898,749,602 | **7.9741%** |

준비 구간(변환+FFT+inverse)은 수정하지 않았다. 각각 843/1,023회, 누적 30,530,742/66,162,982 cycles로 전후 동일했다.

## 같은 실제 입력을 고정한 커널 비교

한 보드 이미지에 fixed/old/new를 넣고 frozen NTRU 입력 19개를 비교했다. 매번 동일 입력을 복원하고 입력 복사는 타이머 밖에서 수행했다. FP64 전후 실행 순서는 번갈아 바꾸었으며 warm-up 10회 + 측정 100회다. 컴파일러가 한쪽 함수만 입력 버퍼에 특수화하지 못하도록 시험용 `noipa`를 적용했다. 실제 성능 펌웨어에는 이 제약을 추가하지 않는다.

아래는 각 logn의 첫 frozen 사례에서 얻은 평균 cycles. 19개 전체 수치는 [summary.json](validation/results/summary.json)에 있다. 이 n은 **NTRU 내부 FFT 크기**이며 FN-DSA 키 크기와 구분해야 한다.

| logn / n | 이전 iFFT | 이후 iFFT | iFFT cycle 감소 | 근사 k 반복 커널 cycle 감소 | 이후 반복 커널 / 고정소수점 시간 |

| 1 / 2 | 14 | 37 | **164.29% 증가** | 6.54% 증가 | 1.863배 |
| 2 / 4 | 340 | 431 | **26.76% 증가** | 7.77% 증가 | 1.738배 |
| 3 / 8 | 1,197 | 1,136 | 5.10% 감소 | 2.13% 감소 | 1.614배 |
| 4 / 16 | 3,431 | 2,898 | 15.53% 감소 | 7.00% 감소 | 1.560배 |
| 5 / 32 | 8,957 | 7,144 | 20.24% 감소 | 9.66% 감소 | 1.557배 |
| 6 / 64 | 22,143 | 17,098 | 22.78% 감소 | 11.31% 감소 | 1.558배 |
| 7 / 128 | 52,801 | 39,948 | 24.34% 감소 | 12.42% 감소 | 1.559배 |
| 8 / 256 | 122,707.01 | 91,550.01 | 25.39% 감소 | 13.22% 감소 | 1.554배 |
| 9 / 512 | 279,717.01 | 206,576 | 26.15% 감소 | 13.83% 감소 | 1.509배 |

logn=1은 산술상 no-op이지만 새 함수의 프롤로그/에필로그 비용이 더 크다. logn=2는 절감할 중간 스케일링이 거의 없고, 최종 루프와 배율 생성 비용이 추가된다. 실제 ELF에서 최종 배율의 8바이트 비트 복사를 `memcpy` 호출로 생성한 것도 확인했다. 작은 크기를 별도 처리하는 개선은 **이번 실험에 섞지 않았다**.

큰 구간이 개선돼도 고정소수점 반복 커널보다는 여전히 약 1.51–1.61배 느리다(logn>=3). 따라서 고정소수점보다 모든 구간이 빨라졌다고 해석하면 안 된다.

| 원본 전체 scheme KAT | **FAIL 유지** | host `test_kat()`에서 KAT-hash 불일치. 키 생성 포함 시험 |
| 정확한 정수 NTRU 방정식·출력 범위 | PASS | 보드 KAT 300키, `fG−gF=q` 및 출력 범위 검사 |
| 생성한 키로 서명·검증·변조 거부 | PASS | 각 FP64 후보 host 200건, 보드 성능 펌웨어 200건; 프로파일 펌웨어도 200건 |
| host↔M55 keygen KAT actual hash | PASS | 전후 각각 300/300 동일 |

80자리 Decimal oracle은 **현재 코드와 같은 Q32 유래 회전 상수**를 사용한다. 진정한 삼각함수 상수의 오차나 NTRU 전체의 수학적 안정성을 증명한 것이 아니다.

- 기존 40개 FFT/iFFT 시험의 최대 절대 오차: FFT `1.838e-11`, iFFT `1.128e-12`.
- 별도 iFFT 80개 고정밀 비교에서 `max_abs_error / max(1,max_abs_oracle)` 최대 `2.5421e-16`.
- 전후 double가 bit-exact이므로 관측 입력에서 이번 변경으로 인한 **추가 수치 오차는 0**이다.
- KAT 기대값을 재생성하거나 불일치를 숨기지 않았다. `BOARD_KAT_DONE result=0`은 모든 감사 작업이 완료됐다는 뜻이며, 바로 뒤 `mismatches=26`을 반드시 함께 읽어야 한다.

## 상수시간 점검

### 정적 범위 점검

[이후 iFFT 디스어셈블리](validation/results/new-perf-ifft.asm)에서:

- 분기 조건은 공개 logn, 공개 레이어/루프 카운터, 공개 배열 범위뿐이다.
- 입력 계수 값으로 분기하거나 비밀 값으로 table/address를 선택하는 새 코드는 없다.
- 실수 비교 `vcmp` 및 FP64 libgcc 소프트웨어 산술 helper가 없다.
- `vadd/vsub/vmul/vnmul/vmla/vnmls.f64`를 사용한다. `vmla/vnmls`는 이 ISA의 비융합 연산이며 `vfma/vfms`는 없다.
- 추가된 `memcpy`의 길이=8, 주소=고정 스택 위치, 내용=공개 logn에서 만든 배율이다.
- butterfly 안의 `×0.5` 명령은 없어지고 마지막 루프의 `vmul.f64`로 이동했다.

이는 해당 함수의 유한 범위 수동 감사이며 전체 keygen의 constant-time 증명이 아니다. 기존의 후보 거부/재시도까지 일정한 실행시간이라고 주장하지 않는다.

### 동적 시험 및 측정 통제

초기 커널 harness에서는 0/일반 입력 간 1–2 cycle 차이가 관측됐다. 원인이 함수 자체인지 시험 준비 과정인지 단정하지 않고 [ct_control](validation/ct_control/kernel_bench.c)로 분리했다.

통제 실험은 모든 입력에 동일한 `memcpy` 준비, 공유 간접호출 타이머, DSB/ISB와 고정 32 NOP 간격, 동일 FPSCR 상태, 전후 교대 순서를 사용한다. logn=1…10, 20종 입력(±0, sparse, cancellation, 서로 다른 정상 지수), warm-up 10회 + 100회 측정.

| logn | 이전 iFFT min=max | 이후 iFFT min=max |
|---|---:|---:|
| 1 | 9 | 27 |
| 2 | 335 | 421 |
| 3 | 1,192 | 1,126 |
| 4 | 3,426 | 2,888 |
| 5 | 8,952 | 7,134 |
| 6 | 22,138 | 17,088 |
| 7 | 52,796 | 39,938 |
| 8 | 122,702 | 91,540 |
| 9 | 279,712 | 206,566 |
| 10 | 628,146 | 460,280 |

**모든 logn에서 시험한 20종 입력 및 100회 반복의 cycle이 일치했다.** 초기 차이는 통제 실험에서 재현되지 않았다. 준비 과정/호출 전 상태 영향과 부합하지만, 정확히 어느 마이크로아키텍처 요인인지까지 확정한 것은 아니다.

유지한 `fp64_div_normal()`도 20종 입력, 각 256회 × 20유효 trial에서 모두 36,864 cycles였다. 이는 정상 domain 산술 정확성과 별개인 시간 진단이며 특수 입력에서도 원래 나눗셈 의미를 보장한다는 뜻은 아니다.

동적 입력 샘플 일치와 정적 분기 검사는 형식 증명·dudect 대규모 통계 검정·전력/전자파 검사를 대체하지 않는다.

## 판단

**Falcon 방식의 최종 정규화는 이 FP64 후보를 개선하는 유효한 방향이다. 다만 원본 KAT 호환성과 고정소수점 대비 반복 구간 성능 문제는 아직 해결되지 않았다.**

현재 후보를 실험 결과로 보존한다. reciprocal 재사용, twiddle/입력 정밀도 변경, reduction_bits 변경, 작은 크기 전용 경로는 이번 구현에 넣지 않았다. 통합 ref를 대체하거나 전체 FP64 전환이 완성됐다고 표시하지 않는다.
