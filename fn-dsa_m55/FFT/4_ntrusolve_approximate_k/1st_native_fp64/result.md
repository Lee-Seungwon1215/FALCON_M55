# 첫 측정 기록 — 아래 수치는 후속 수정 전의 역사적 결과

측정일: 2026-09-18. **기본 FP64 구현과 비교 실험 완료 / 채택 보류.**

핵심 결과는 **역수 준비는 빨라졌지만 반복 FFT 계산은 느려졌다**는 것이다.
또한 기존 keygen KAT 300개 중 26개가 달라졌고, native 나눗셈의 입력별
시간 차이를 확인했으므로 KAT·상수시간 조건을 모두 통과한 구현은 아니다.

원본 `../ref`와 `fn-dsa_m55/ntt_opt`는 수정하지 않았다.
수작업 assembly, 2~5단계 최적화, 다른 폴더로의 채택·통합은 하지 않았다.

## 1. 무엇을 비교했나

| 비교군 | 내용 |
|---|---|
| 고정소수점 | `../ref`: 실험 전 `ntt_opt`와 모든 루트 C/H/S 파일 hash 일치. 기존 Q32.32 산술 |
| FP64 | 이 폴더: `solve_NTRU_intermediate()`의 **④ 근사 k 계산만** native double C로 변경 |

변경한 암호 코드 파일은 `kgen_inner.h`, `kgen_poly.c`, `kgen_fxp.c`, `kgen_ntru.c`뿐이다.
NTT/RNS·CRT·Bezout 및 정확한 정수 해 갱신 연산, ⑤ depth0,
키 후보 검사, 서명·검증 코드는 원본과 동일하다. 모든 `.s` 파일도 동일하다.

기존 입력의 Q32.32 창과 root 양자화 값을 유지하고, 해당 값을 **수치적으로** double로
변환했다. uint64 비트를 double 비트로 재해석한 것이 아니다.
FFT radix-2 계산 순서, 복소 3곱셈, 두 번 나눗셈, iFFT 단계별 1/2 및
기존 스케일·반복 계획을 유지했다. 상수 정밀도 개선이나 역수 재사용은 미적용이다.

발산한 후보가 FP64→int32 변환 또는 후속 정수 갱신을 넘치게 하지 않도록
추가한 안전 검사는 아래 5절에 설명하며, **측정 시간에 포함**했다.

## 2. 동일 입력의 계산 구간 비교 — 산술 효과를 보는 표

실제 NTRU 실행의 입력을 고정해 **한 펌웨어 안에서** 두 구현에 각각 넣었다.
각 logn에서 서로 다른 입력 2개, 추가 KAT 진단 입력 1개: 총 19개 시험 레코드.
대표 18개는 실제 반올림 결과가 0이 아닌 입력이며, 추가 진단 입력은 대표 입력과
겹칠 수 있다. 각 입력 10회 warm-up 후 100회, 두 backend의 실행 순서를 번갈았다.

표는 logn별 두 입력의 평균 cycle/call이다. 입력 버퍼 설정은 계측 밖이며,
big-integer limb 추출은 제외했다. FP64 반올림·범위 검사는 포함했다.

- **준비:** `FFT(f) → 2^e·adj(f)/|f|²`를 한 번 계산.
- **반복:** `FFT(F) → 준비 값과 복소 곱셈 → iFFT → round(k)`를 한 번 계산.

| 내부 FFT 크기 n (logn) | 준비: 고정소수점 | 준비: FP64 | FP64 준비 속도 | 반복: 고정소수점 | 반복: FP64 | FP64 반복 소요시간 |
|---:|---:|---:|---:|---:|---:|---:|
| 2 (1) | 3,597 | 259 | 13.89배 빠름 | 169 | 331 | 1.96배 |
| 4 (2) | 7,358 | 701 | 10.50배 빠름 | 686 | 1,226 | 1.79배 |
| 8 (3) | 14,913 | 1,701 | 8.77배 빠름 | 1,838 | 3,339 | 1.82배 |
| 16 (4) | 30,214 | 4,062 | 7.44배 빠름 | 4,553 | 8,294 | 1.82배 |
| 32 (5) | 61,232 | 9,531 | 6.42배 빠름 | 10,869 | 20,217 | 1.86배 |
| 64 (6) | 124,134 | 21,988 | 5.65배 빠름 | 25,337 | 47,780 | 1.89배 |
| 128 (7) | 251,704 | 49,965 | 5.04배 빠름 | 58,009 | 110,383 | 1.90배 |
| 256 (8) | 510,410 | 112,070 | 4.55배 빠름 | 130,889 | 250,586 | 1.91배 |
| 512 (9) | 1,034,988 | 248,607 | 4.16배 빠름 | 291,785 | 561,029 | 1.92배 |

**오른쪽 열은 속도 향상률이 아니라 소요시간 비율**이다. 1.92배는 약 92% 느리다는 뜻이다.
표의 n은 전체 키 크기가 아니다. 512 키생성의 ④는 최대 n=256,
1024 키생성의 ④는 최대 n=512다. `logn=1`은 FFT 자체가 no-op인 경계 경로다.

따라서 “FP64를 사용하면 FFT가 무조건 빨라진다”는 결론은 나오지 않았다.
준비 구간에는 고정소수점 나눗셈이 포함되므로 큰 이득이 있지만,
더 많이 반복하는 FFT·곱셈·iFFT·반올림 묶음은 이번 기본 C 구현에서 손해였다.
나눗셈 한 개나 FFT 한 개만의 독립 속도로 이 표를 해석하면 안 된다.

원시값: [최종 kernel raw.log](validation/results/kernels/20260918T045553Z/raw.log),
[고정 입력/80자리 oracle](validation/build/host/frozen-oracle.json).

## 3. 전체 키생성 시간 — 순수 산술 개선율과 구분

각 크기에서 `test0`~`test99`라는 서로 다른 seed 100개를 사용했다.
단위는 cycle/call, 중앙값은 정렬한 100개 중 인덱스 50의 upper median이다.
감소율은 `(고정소수점−FP64)/고정소수점 × 100`이다.

| 키 크기 | 고정소수점 평균 | FP64 평균 | 평균 cycle 감소 | 고정소수점 중앙값 | FP64 중앙값 | 중앙값 변화 |
|---:|---:|---:|---:|---:|---:|---|
| 512 | 57,007,002.15 | 56,136,451.98 | 1.5271% (1.0155배) | 48,150,560 | 50,473,330 | **4.8240% 느려짐** |
| 1024 | 243,375,295.54 | 223,032,366.38 | 8.3587% (1.0912배) | 195,772,943 | 189,590,380 | 3.1580% 빨라짐 |

**주의:** 같은 seed여도 일부 출력 키와 후보 재시도 횟수가 달라졌다.
이 숫자에는 산술 속도뿐 아니라 반올림·후보 채택 경로·안전 검사 효과도 섞였다.
따라서 “FP64 계산만으로 키생성이 8.36% 개선됐다”고 주장할 수 없다.
특히 512는 평균은 감소했지만 중앙값은 증가했다. 표본 100개의 관측값이며
입력 모집단 전체의 성능 보장 또는 신뢰구간 추정이 아니다.

## 4. 실제 키생성 중 ④의 비중

별도 profile 펌웨어에서 input conversion을 포함해 계측했다.
분모는 **그 profile 펌웨어의 전체 키생성 100회 cycle 합**이다.
타이머 훅의 오버헤드가 포함되며, 위 3절의 무계측 시간과 섞지 않았다.
⑤ depth0의 FFT나 다른 NTRU 연산은 여기에 포함되지 않는다.

| 키 크기 | 구현 | ④ 준비 호출 수 | 준비 합계 cycles | 전체 keygen 비중 | ④ 반복 호출 수 | 반복 합계 cycles | 전체 keygen 비중 |
|---:|---|---:|---:|---:|---:|---:|---:|
| 512 | 고정소수점 | 879 | 108,300,980 | 1.898% | 92,174 | 473,859,599 | 8.304% |
| 512 | FP64 | 843 | 27,486,645 | 0.489% | 86,136 | 789,708,404 | 14.054% |
| 1024 | 고정소수점 | 1,107 | 220,166,575 | 0.904% | 251,354 | 1,343,744,383 | 5.518% |
| 1024 | FP64 | 1,023 | 60,278,413 | 0.270% | 218,396 | 2,168,095,037 | 9.715% |

FP64의 준비 구간은 줄었지만, **④ 두 구간의 시간 합은 증가**했다.
호출 횟수도 같지 않으므로 순수 산술 비교는 2절을 우선해서 본다.
후보 경로 변화로 다른 NTRU 작업량도 바뀌어 전체 평균은 반대로 감소할 수 있다.

### 구현 중 발견해 수정한 두 가지 범위 문제

1. 일부 버려질 후보에서 FP64 iFFT 결과가 int32 범위를 넘었다.
   `fp64_round_i32_checked()`가 변환 전에 안전하게 마스킹하고 후보 실패를 표시한다.
2. int32 범위 안이어도 n=2/4/8의 기존 정수 갱신은 여러 곱을 int64에 누적한다.
   FP64 후보의 큰 k로 실제 overflow가 검출됐으며, baseline의 같은 입력 집합은 통과했다.
   `fp64_k_update_ok()`에서 `|k[i]| <= floor((2^31−1)/n)`을 확인해
   해당 누적합이 int64 안전 범위에 있도록 후보를 거부한다. 정수 갱신 수식은 바꾸지 않았다.

각 검사는 공개된 크기만큼 전부 순회한 뒤 후보 단위로 거부한다.
최종 host 진단의 200개 키 + 크기별 warm-up에서 3,298,860개 반올림 입력을 확인했다.
범위 밖 248계수를 안전하게 처리했고, 작은 크기 정수 갱신 검사에서 43개 벡터가 거부됐다.
두 수치는 실패 후보 수를 뜻하지 않으며 중복될 수 있다.

ASan은 이 Mac의 런타임 초기화 단계에서 abort하여 **검사하지 못했다**.
전체 UBSan도 복사본의 수정하지 않은 SHAKE 비정렬 load 및 host NEON mq 경로에서
중단되어, host에서 upstream portable SHAKE load를 선택하고 수정한 TU만 검사했다.
최종 표적 검사에서는 sanitize 범주를 끄지 않았다. 실패 로그도 `validation/build/host/`에 보존했다.

### KAT가 달라진 대표 원인

512 `test43`의 첫 k 차이를 동일 f/F 입력에서 추적했다.

| 항목 | 고정소수점 | FP64 | 80자리 oracle |
|---|---:|---:|---:|
| depth=7, logn=2, 한 계수의 근삿값 | 24.55756608699 | 23.44621494072 | 23.44621498916 |
| 반올림한 k | 25 | 23 | 23 |

이 사례에서 baseline은 두 번째 후보를 depth7에서 거부하고 네 번째 후보를 채택했지만,
FP64는 두 번째 후보를 채택했다. 그래서 f,g와 최종 키까지 달라졌다.
즉, **FP64가 더 정밀하게 계산하더라도 기존 KAT가 자동으로 같아지는 것은 아니다.**
26개 불일치 전부의 원인을 개별 증명했다는 뜻은 아니다.
자세한 추적은 [diagnosis.json](validation/build/trace/diagnosis.json)에 있다.

## 6. 상수시간 확인의 범위와 한계

추가한 FFT loop·주소는 logn/공개 인덱스로 결정된다. 입력 변환은 기존 일정한 limb 순회를
유지하며, 반올림/범위 검사는 계수별 조기 종료 없이 mask/predication으로 구현됐다.
하지만 거부 후 재시도하는 **키생성 전체가 항상 같은 시간이라는 주장은 하지 않는다**.
새 범위 검사 역시 후보 수준의 거부 분기를 추가한다.

M55에서 `probe_div(a,b)`가 실제 `VDIV.F64; BX LR`로 컴파일됨을 확인하고,
동일 함수·주소에서 256회씩 20개 측정 trial을 실행했다.

| 입력 | 256회 루프 min~max cycles |
|---|---:|
| `0 / 1` | 3,847~3,847 |
| `1 / 1`, `-1 / 1` 및 시험한 나머지 9개 비영 입력 쌍 | 10,503~10,503 |

루프·호출·volatile load/store 비용을 포함한 값이며 단일 나눗셈의 절대 latency가 아니다.
동일 위치에서 입력만 바꾸어 시간 차이가 났으므로 native division을 무조건
상수시간 primitive로 취급할 수 없다.

실제 host NTRU 200키+warm-up에서 검사한 분자 156,986개에는 0이 없었다.
따라서 이 시험만으로 실제 키에서 같은 timing 차이가 발생했다고 단정하지 않는다.
반대로 모든 가능한 비밀 입력에서 0/특수값이 배제된다는 증명도 없으므로
**상수시간 PASS로 인증할 수 없다**. 전력/EM TVLA·형식 검증도 수행하지 않았다.

## 7. 보드·빌드·메모리 조건

- 보드: 연결된 NUCLEO-N657X0-Q, Cortex-M55 r1p1, 지정 ST-LINK만 사용.
- CPU 800 MHz, I/D cache OFF. TCM control `0x99`, ECC 활성/오류 상태 확인.
- ITCM/DTCM 각각 256 KiB 구성. 기존 공통 플랫폼의 정책대로
  **실행 코드는 ITCM 하위 128 KiB**, 상수·데이터·스택은 DTCM 배치.
- 양쪽 모두 같은 고정 버전 Zephyr/플랫폼 loader/컴파일러 GCC 15.2.1.
- `-O3 -mfpu=fpv5-d16 -ffp-contract=off -fno-fast-math -fno-strict-aliasing`.
- 기존 M4/M55·RNS assembly 활성 상태 유지. 이번에 직접 작성한 산술은 C뿐이다.
- FPSCR round-to-nearest, FP64 flush-to-zero OFF 확인.
- DWT CYCCNT, 키생성 구간 IRQ OFF, 출력·서명 검사는 계측 밖.
- 전체 측정은 100개 seed, 크기별 warm-up 1회. 커널은 입력별 warm-up 10회 + 100회.
- ELF에 hardware FP64 산술 존재, FP64 soft helper 없음, fused-FMA 명령 없음 확인.
- 두 전체 펌웨어의 배치 정책은 같지만 함수별 주소를 동일하게 고정한 시험은 아니다.

| 전체 성능 펌웨어 | ITCM 코드/이미지 사용 | DTCM 사용(예약 stack 포함) |
|---|---:|---:|
| 고정소수점 | 101,588 B | 220,232 B |
| FP64 | 102,280 B | 236,616 B |
| 증가 | **692 B** | **16,384 B** |

FP64 root 표를 추가했기 때문에 DTCM이 16 KiB 증가했다.
최종 DTCM 잔여량은 25,528 B, 코드도 ITCM 하위 128 KiB 제한 내다.
main stack 예약은 65,536 B다. 이번 결과는 linker 예약량이며 새로운 stack high-water
측정이나 모든 입력의 최대 stack 사용량 증명은 아니다.
링커의 `FLASH` 표기는 이 구성에서 ITCM 실행 영역을 가리키며, 실제 flash 실행이 아니다.

## 판단

**기본 FP64 전환의 효과는 확인했지만, 기존 ref를 교체할 단계는 아니다.**
현재는 수치·성능을 비교할 실험 기준점으로 보관한다.
채택하려면 기존 KAT 호환성을 유지할 것인지에 대한 정책과 실제 피연산자 범위에 대한
상수시간 근거가 먼저 필요하며, 이번 작업에서는 그 조건을 임의로 완화하지 않았다.
