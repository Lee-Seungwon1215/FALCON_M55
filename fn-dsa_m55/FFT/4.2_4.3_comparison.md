> 현재 소스의 결과는 [Q32 보정 후 비교](4.2_4.3_q32_rules_result.md)를 참조한다.
> 보정 후 두 후보 모두 원본 300개와 추가 300개가 일치했지만 성능은 느려졌다.

`ntt_opt`, `M55_ref`, 4.1 본체는 변경하지 않았다.

## 구현 범위

두 후보 모두 사용자가 복사한 `ntt_opt`에서 **각각 독립적으로** 구현했다.
B를 완성한 다음 C로 변환한 것이 아니며, 다른 후보의 암호 소스를
빌드할 때 가져오지 않는다. 공통으로 검증했던 4.1의 MVE butterfly와
회전상수는 각 폴더에 직접 작성/이식했다.

| 구분 | B: `4.2_ntrusolve_q32fpq32` | C: `4.3_ntrusolve_intfpint` |
| --- | --- | --- |
| 시작 | 원본 정수 → Q32 → DS | 원본 정수 → DS 직접 생성 |
| 중간 | FFT → 역수/점별 연산 → iFFT를 DS로 유지 | FFT → 역수/점별 연산 → iFFT를 DS로 유지 |
| 끝 | DS → Q32 → 기존 `fxr_round()` → 정수 k | DS → 정수 k 직접 생성 |
| 적용 | NTRU intermediate/depth0, `logn >= 4` | NTRU intermediate/depth0, `logn >= 4` |
| 작은 크기 | `logn < 4`는 원본 고정소수점 | `logn < 4`는 원본 고정소수점 |

DS(double-single)는 실수 하나를 `hi + lo` 두 FP32로 표현한다.
복소수 하나는 실수부 두 float + 허수부 두 float, 총 네 float이다.
FFT butterfly는 MVE FP32 어셈블리, 주변 곱셈/역수는 현재 scalar DS이다.
따라서 **주변 연산까지 모두 MVE화한 최종 구현이라는 뜻은 아니다.**

공통으로 이미 채택했던 FP64 invnorm(e=0)만 후보 검사에 반영했다.
후보 검사의 FFT/iFFT는 원본 고정소수점이다. NTT·CRT·Bezout·정수 갱신,
서명/검증의 소스는 `ntt_opt`와 같다. C도 원본의 비밀 스케일에 대한
전체 limb scan/마스크 선택과 입력 비트 절삭 규칙을 유지한다.

원본에서 바뀐 암호 파일은 각 폴더의 `kgen_ntru.c`, `kgen_fxp.c`이며,
`kgen_ds.h`, `kgen_fft_mve.c`, `kgen_fft_cm55.s`를 추가했다.
각 함수가 소유하는 독립 DS 버퍼 2개는 총 16 KiB이다.

## 1차 KAT 관찰 — 최종 채택 판정과 구분

최초 B와 C는 각각 300개 중 **294개 일치, 6개 불일치**였다.
모든 생성 키의 정확한 NTRU 방정식 검사는 통과했다.
불일치: 512의 `test58`, `test78`; 1024의 `test7`, `test65`, `test79`, `test80`.
두 후보의 300개 출력 해시는 서로 전부 같았다.

이것은 입출력 경계 차이보다 공통 continuous DS 계산의 수치 규칙을
조사할 근거이지, 모든 입력의 동등성이나 오류 부재를 증명한 것은 아니다.
원본은 곱셈에서 Q32 절삭, 나눗셈에서 Q32 반올림, iFFT에서 단계별 half를
수행한다. DS의 더 높은 중간 정밀도나 마지막 한 번의 Q32 변환만으로
이 계산 규칙이 자동으로 같아지지는 않는다.

초기 로그:

- B: `4.2_ntrusolve_q32fpq32/validation/results/kat/20260927T055652Z/`
- C: `4.3_ntrusolve_intfpint/validation/results/kat/20260927T055809Z/`

## 재현 경로와 주의

각 후보의 `validation/build.sh`와 `validation/run_board.py`를 사용한다.
복사되어 남은 루트 `build/`, `profiling/`, 옛 Makefile/프로파일 문서는

KAT 불일치가 있으면 빠르더라도 채택 조건 충족으로 표시하지 않는다.
유효한 키의 생성/서명·검증 성공과 **원본 KAT 동일성**은 별도 항목이다.
유한 입력 타이밍 검사와 정적 검사는 전체 상수시간의 수학적 증명이 아니다.
원본 키생성 자체도 거부/재시도에 따라 실행 시간이 변한다.

출력이 같다는 것만으로 모든 중간 이력까지 같음을 보장하지는 않는다.

## 커널과 연속 구간은 따로 해석해야 한다

C의 같은 ELF 내 원본 고정소수점 대비 **DS 내부 FFT/iFFT**:
아래에는 입출력 변환이 포함되지 않는다.

| 커널 | n | 원본 cycles | DS cycles | 속도 배수 |
| --- | ---: | ---: | ---: | ---: |
| FFT | 512 | 125,919 | 89,771 | 1.403배 |
| iFFT | 512 | 143,342 | 97,783 | 1.466배 |
| FFT | 1024 | 280,385 | 198,492.01 | 1.413배 |
| iFFT | 1024 | 318,476.01 | 216,141 | 1.473배 |

C에서 정수 직접 입력 생성은 원본 `poly_big_to_fixed`보다 약 1.98배,
마지막 `k` 생성은 기존 `fxr_round` 배열보다 약 15.5배 시간이 걸렸다.
점별 DS 복소곱도 약 36.7% 느렸다. 반면 DS 역수 준비는 해당 합성 입력에서
약 10.47배 빨랐다. **변환 배열을 없앴다고 경계 계산 비용까지 자동으로 없어지지 않는다.**

B의 Q32 입출력을 **포함한** 반복 근사 구간
`import → FFT → pointwise multiply → iFFT → export`:

| n | 원본 cycles | B cycles | 시간 감소 |
| --- | ---: | ---: | ---: |
| 512 | 286,806 | 268,528 | 6.37% |
| 1024 | 633,942.03 | 576,422 | 9.07% |

이 합성 입력에서는 최종 k 차이가 각각 387 / 668 계수 관측되었으므로,
시간 개선과 수치 일치를 혼동하면 안 된다.
C 연속 구간은 역수 준비와 정수 입력 생성까지 포함하는 별도 하네스이므로
B의 위 표와 절대 사이클을 직접 비교하지 않는다.
전체 logn=4..10 및 연산별 표는 각 후보의 `result.md`에 기록했다.

## KAT 원인 분리에서 확인한 것

실제 오류도 발견해서 수정했다. B export의 `hi=2^-33, lo=-2^-62`는
기대 Q32 raw 0이지만 이전에는 1이었다. TwoSum 잔차 보존으로 수정했고,
보드 회귀 검사에서 raw 0을 확인했다. C도 음수 tiny low를 버리는 경계
연산과 비밀값 조건 분기를 수정했다. **수정 뒤에도 KAT 6개 불일치는 동일했다.**

동결해 둔 실제 입력에 대한 별도 진단에서는 다음 규칙 차이가 확인됐다.

1. 작은 제곱합: `1024-test7` 예에서 원본 분모는 Q32 raw 9,
   절삭하지 않은 제곱합은 약 2.319e-9였다. 원본은 약 9.6% 작은 분모로 나눈다.
2. 0으로 절삭되는 분모: `1024-test79` 입력은 원본 Q32 제곱합이 0이지만,
   연속 계산은 약 8.00e-11이다. 원본 정수 나눗셈의 특수 동작과 일반 역수는 다르다.
3. 범위 감김: residual `512-test58` 진단 입력에서 점곱의 감기지 않은 값은
   약 7.97e9까지 커진다. 원본 Q32의 modulo-2^64 감김과 DS 계산은 다르다.

C의 **진단 전용** 원본 중간값 주입 시험:

| 동결 입력 묶음 | DS 원형 | FFT만 원본 값 | 역수까지 원본 값 | 점곱까지 원본 값 |
| --- | --- | --- | --- | --- |
| 처음 5개 사례의 k 불일치 수 | 30/12/15/9/1 | 30/12/15/9/1 | 모두 0 | 모두 0 |
| residual 512-test58 | 64 | 63 | 63 | 0 |

이는 특정 구간의 수치 규칙이 결과를 바꾼다는 근거다.
중간값 주입은 생산 코드에 없으며, fallback이나 KAT 기대값 변경도 하지 않았다.
진단 입력은 과거에 캡처한 6개로 현재 실패 목록과 1:1 대응하지 않는다.
`1024-test74`가 포함되고, 현재 실패한 `1024-test65`의 첫 반복을 이번에
직접 캡처하지는 않았다. 따라서 **현재 모든 실패의 원인 또는 모든 입력 동등성을
완전히 증명했다고 주장하지 않는다.**
